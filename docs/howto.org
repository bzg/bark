* 🐕 BARK --- Bug And Report Keeper

BARK monitors a mailbox and converts incoming emails into reports.
Subsequent emails in the same thread can update the status of that
report using predefined trigger keywords. Admins and maintainers can
update reports by writing directly to the monitored inbox, manage
roles, and receive periodic digest emails.

* As a user
** Bug, Patch, Request

As a user, you can report bugs, propose patches and make other
requests:

- You create a bug report by adding =[BUG]= to the subject.
- You send a patch by adding an inline or attached patch.
- You can also create a =[POLL]=, share a feature request =[FR]= or a
  =[TODO]=.

See below the list of [[#report types][report types]].

** Updating reports

State changes occur when a reply in the same thread contains a
case-senstive trigger keyword at the start of a line, followed by a
punctuation mark (=.= =,= =;= =:=). For example, a reply to a bug report with
a line starting with =Confirmed.= marks the bug as "acked"; a reply to a
patch with a line starting with =Applied.= marks the bug as "closed".

See the [[#Triggers keywords][Triggers keywords]] below for the full list.

** Voting on requests

Requests (=[POLL]=, =[FR]=, =[TODO]=, etc.) support voting: 

- =+1= or =1+= means "I support"
- =-1= or =1-= means "I don't support"
- =-0=, =0-=, =+0= or =-0= means "I abstain"

* As a maintainer or admin
** Announcements, releases, changes

In addition to bugs, patches, and requests, maintainers can make
general announcements, share a release, or announce an upcoming change
in a future release.

** Undoing updates

Maintainers can also "undo" an update:

: Unacked.
: Unowned.
: Unclosed.
: Unurgent.
: Unimportant.
: Undeadline.

** Setting a deadline

Maintainers can set a deadline on a report by writing the following
in the body of a reply:

: Deadline: 2026-03-10.

The date must be in =yyyy-MM-dd= format, followed by a punctuation
mark.  The deadline appears in JSON exports, Org output (as a proper
=DEADLINE:= line), and notification emails.

To remove a deadline:

: Undeadline.

** Updating offlist

Also, maintainers can write directly to the watched inbox to update a
report without notifying the list.

For example, the maintainer can clean up old issues by marking them as
=Cancelled= in the body of a reply sent to the monitored inbox, rather
than to the entire list. This is also useful for reclassifying emails:
if someone forgot the =[BUG]= prefix, a maintainer can edit the subject
and resend the email to the BARK inbox.

** Acting as an update proxy

Maintainers can also write directly to the BARK inbox to act as
"proxies" and update a report as if they were users:

: Acked-by: a-user@example.com
: Owned-by: a-user@example.com
: Closed-by: a-user@example.com
: Urgent-by: a-user@example.com
: Important-by: a-user@example.com

** Managing roles and permissions

Here is how the permissions work:

- There is only one admin per source.
- The admin and maintainers can promote users as maintainers.
- The admin can demote maintainers as users.
- The admin and maintainers can ignore users.
- The admin can "unignore" users.

Roles and permissions are set by writing to the BARK inbox:

#+begin_example
Add maintainer: dev@example.com        (admin or maintainer)
Remove maintainer: dev@example.com     (admin only)
Ignore: spammer@example.com            (admin or maintainer)
Unignore: user@example.com             (admin only)
#+end_example

* Report types

Reports are detected from email subject labels:

| Tag                                             | Type           |
|-------------------------------------------------+----------------|
| =[BUG]= =[BUG version]=                             | bug            |
| =[PATCH]= =[PATCH n/m]= =[PATCH topic n/m]=           | patch          |
| =[POLL]= =[FR]= =[TODO]=                              | request        |
| =[ANN]= =[ANNOUNCEMENT]=                            | announcement   |
| =[REL]= =[RELEASE]= =[REL version]= =[RELEASE version]= | release        |
| =[CHG]= =[CHANGE]= =[CHG version]= =[CHANGE version]=   | change         |

When a =[REL version]= report is created, any open =[CHG version]= reports
with the same version are automatically closed.

Announcements, releases and changes require maintainer permission.

** Customising subject labels

The subject labels in the table above are the built-in defaults. You
can override them globally or per source in =config.edn= via =:labels=.
Specify only the types you want to change; unspecified types keep
their defaults.

#+begin_src edn
;; Global override (applies to all sources)
:labels {:bug     ["BUG" "DEFECT"]
         :request ["POLL" "FR" "TODO" "RFE"]}
#+end_src

#+begin_src edn
;; Per-source override (inside a source map)
{:name "my-list"
 :labels {:announcement ["ANN" "NEWS"]}}
#+end_src

Per-source settings take precedence over the global =:labels=, which in
turn take precedence over the built-in defaults.

* Trigger keywords

State changes are detected by trigger keywords within the body of a
response down the thread, at the beginning of the line, followed by a
punctuation mark (=.= =,= =;= =:=):

| Trigger keyword | Effect on report            |
|-----------------+-----------------------------|
| =Approved.=       | acked (bug, patch, request) |
| =Confirmed.=      | acked (bug)                 |
| =Reviewed.=       | acked (patch)               |
| =Handled.=        | owned                       |
| =Fixed.=          | closed (bug)                |
| =Applied.=        | closed (patch)              |
| =Done.=           | closed (request)            |
| =Closed.=         | closed (request)            |
| =Canceled.=       | closed (all)                |
| =Cancelled.=      | closed (all)                |
| =Urgent.=         | urgent                      |
| =Important.=      | important                   |

You can use multiple keywords in the same email, one per line.

** Report statuses and priority

All reports can be in a combination of three states:

- *Acked* --- someone took the next reasonable action (confirmed a bug, reviewed a patch, approved a request).
- *Owned* --- someone claimed ownership of this report.
- *Closed* --- the report is resolved (fixed, applied, done, or canceled).

Announcements, releases, and changes can only be closed.

** Status (as number)

When the status is represented as a numeric value, it is computed like
this:

| (Un)acked  | (0)1 |
| (Un)owned  | (0)2 |
| (Un)closed | (4)0 |

So a acked, unowned and open report is =1+0+4 = 5=.

** Priority (as number)

Prority is never set directly, it is derived from whether the report
is marked as urgent or important. When the prority is represented as a
numeric value, it is computed like this:

| (Un)important | (0)1 |
| (Un)urgent    | (0)2 |

So an important and urgent report is =1+2 = 3=.

** Customising trigger keywords

You can customize trigger keywords globally or per source:

 : :triggers {:bug {:closed ["Canceled" "Fixed" "Resolved"]}
 :            :patch {:acked ["Approved" "Reviewed" "LGTM"]}}

* Exploring reports

The BARK instance can expose reports as HTML, JSON and Org formats.

** Browsing Bark reports online

A web interface let you navigate Bark reports.

The search field has a minimal syntax:

| Long form                   | Short | Explanation                            |
|-----------------------------+-------+----------------------------------------|
| from:me@example.org         | f:    | Reports from me@example.org            |
| acked:me@example.org        | a:    | Reports acked by me@example.org        |
| owned:me@example.org        | o:    | Reports owned by me@example.org        |
| closed:me@example.org       | c:    | Reports closed by me@example.org       |
| urgent:me@example.org       | u:    | Reports marked urgent by me@example.org    |
| important:me@example.org    | i:    | Reports marked important by me@example.org |
| subject:match               | s:    | Reports matching subject               |
| priority:[0-4]              | p:    | Reports matching priority level 0 to 4 |
| mid:<messageid>             | m:    | Report open with <messageid>           |
| date:3d..                   | d:    | Reports from 3 days ago                |
| date:2023-01-01..2023-12-31 | d:    | Reports from 2023-01-01 to 2023-12-31  |
| match1 \vert match2             |       | Reports matching "match1" or "match2"  |
| *                           |       | Wildcard for from/acked/owned/closed/urgent/important |

** The =bone= CLI tool and =gnus-bone.el=

[[https://codeberg.org/bzg/bone][bone]] lets you browse and filter BARK reports interactively from the
terminal.

[[https://codeberg.org/bzg/gnus-bone][gnus-bone.el]] lets you explore BARK reports from within [[https://gnus.org/][Emacs Gnus]].
* Notifications

BARK can send periodic email notifications to admins and maintainers
with a summary of open reports. Notifications are never sent to
regular users.

Notifications require SMTP configuration (see [[#config][Config]]) and are sent via
=bb notify=, typically from a cron job. Each notification email contains
two sections: open bugs/patches/requests owned by the recipient, and
all unacked & unowned bugs/patches/requests by anyone.

** (Un)subscribing

Admins and maintainers are subscribed by default when =bb digest= runs
for the first time. To unsubscribe, send an email to the BARK inbox
with this body:

#+begin_example
Notify: off
#+end_example

To re-subscribe:

#+begin_example
Notify: on
#+end_example

** Setting preferences

Notification preferences are set via the same =Notify:= command.
Parameters can be combined on a single line:

| Parameter | Description                        | Default |
|-----------+------------------------------------+---------|
| =d:N=       | Receive notifications every N days |      30 |
| =p:N=       | Minimum priority (0--3)            |       1 |
| =s:N=       | Minimum status (0--7)              |       1 |

Examples:

#+begin_example
Notify: d:7                 — every 7 days
Notify: d:1                 — daily
Notify: p:1                 — only important reports
Notify: d:3 s:4 p:2         — every 3 days, only open reports with priority >= 2
#+end_example

Like role commands, =Notify:= commands are only processed from direct
emails, not from the mailing list.
