#+title: BARK! Another Report Keeper
#+subtitle: User manual
#+options: toc:1

* EmBARK

BARK monitors a mailbox and converts incoming emails into reports.

Subsequent emails in the same thread can update the status of that
report using predefined commands. Maintainers can also update reports
by writing directly to the monitored inbox, manage roles, and receive
periodic digest emails.

BARK expose reports as a HTML website and export data to various
formats.

* Example

Imagine Alice sends this email to a mailing list:

: From: alice@email.com
: Subject: [BUG] Wrong output
: To: project-mailing-list@lists.org
: Date: Fri, 6 Mar 2026 16:31:14 +0000
: 
: Hi all,
: 
: when doing X, I get the wrong output, probably a bug.

Then Bob replies:

: From: bob@email.com
: Subject: Re: [BUG] Wrong output
: To: alice@email.com
: Cc: project-mailing-list@lists.org
: Date: Fri, 6 Mar 2026 16:38:42 +0000
: 
: > when doing X, I get the wrong output, probably a bug.
: 
: Confirmed, I see this too, this should not happen.

And Eve, the maintainer, concludes:

: From: eve@email.com
: Subject: Re: [BUG] Wrong output
: To: project-mailing-list@lists.org
: Date: Fri, 6 Mar 2026 16:42:03 +0000
: 
: >> when doing X, I get the wrong output, probably a bug.
: 
: > Confirmed, I see this too, this should not happen.
: 
: Fixed in commit bc12c0c, thanks to both of you!

What happened here?

1. Someone reported a bug
2. Someone else confirmed it
3. The maintainers fixed it

Alice, Bob and Eve all have access to the same information and receive
all emails. When things are running smoothly, as in the above example,
there is no real need for a bug tracker. However, when the mailing
list receives bug reports, patches and general discussions, it is
necessary to keep all of this information in a database. This is what
BARK is for: storing reports sent to a mailbox in a database.

* Principles

- *One place* :: Reports and their discussions belong in one source
  -- the mailing list, which BARK indexes.  The tracker's job is to
  filter noise, not to host a separate conversation.

- *Email-native* :: No account, no platform, no vendor lock-in.
  Users work in whatever mail client they already use, and the
  mailing list archive *is* the tracker history -- BARK simply
  indexes it.

- *Immutable* :: Every state change is encoded in an email, so the
  whole tracker state can be rebuilt from the mailbox at any time.
  No tracker backups to manage, no DB migrations between versions
  -- the mailbox is the source of truth.

- *Local-first* :: Companion tools (=bone= TUI, =gnus-bone.el=,
  =notmuch-bone.el=) let users consume BARK data from their existing
  environment instead of imposing a new interface.

- *KISS* :: Fixed vocabulary, deliberately: =acked=, =owned=, =closed=
  for status; =urgency= and =importance= for priority.  No custom
  =WONTFIX-MAYBE= status, no manual P0 -- this prevents the label
  proliferation that eventually breaks trackers.

* As a user
** Bug, Patch, Request

The subject label decides the report's type: =[BUG]=, =[PATCH]=,
=[POLL]= / =[TODO]= for requests (and a few more, see
[[#report-types][report types]] below).

A patch report is created in two cases, and only two:

1. The subject starts with =[PATCH]= -- either directly, or as
   =Re: [PATCH] ...= when the reply also carries a =.patch=/=.diff=
   attachment (the v2/v3 reply workflow).
2. The email attaches a =git format-patch= file -- the patch's own
   inner =Subject:= line starts with =[PATCH]=.

Anything else is *not* a patch report: a bare inline diff, a quick
=git diff > x.patch= attached in a reply without re-labelling, a
quoted diff in a discussion.  If you want BARK to track your fix as
a patch, attach a real =git format-patch= file *or* relabel the
subject with =[PATCH]=.

Attaching a patch to a =[BUG]= or =[FR]= email does not change the
report's type; the patch is stored as metadata on the parent.

** Setting a topic

Topics can be set in two ways:

- *Inside the label*: =[BUG parser]= sets topic to "parser".
- *Colon prefix after the label*: =[BUG] parser: crash on empty input=
  also sets topic to "parser" (the first colon-delimited segment after
  the closing bracket).

Anyone can also change the topic of an existing report by replying
with:

: Topic: new-topic.

Or remove it with =No topic.=.

** Updating reports

State changes occur when a reply in the same thread contains a
case-sensitive command keyword at the start of a line, followed by
punctuation (=.= =,= =;= =:= =?= =!=), whitespace, or end of line.

For example, a reply to a bug report with a line starting with
=Confirmed.= marks the bug as "acked"; a reply to a patch starting
with =Applied.= or =Fixed.= marks the patch as "closed".

The =Urgent= and =Important= keywords are stricter: they require
punctuation or end of line (not whitespace), because words like
"Important" appear too often in ordinary prose (e.g. "Important
note:").

Email signatures (delimited by =-- = per RFC 3676) are stripped before
scanning, so command-like words in signatures are ignored.

See the [[#all-commands][complete list of commands]] below for the full list.

** Retracting your own updates

If you previously marked a report with =Acked.=, =Owned.=, =Closed.=,
=Urgent.= or =Important.=, you can retract your own action by replying
with the matching "Not" command:

: Not acked.
: Not owned.
: Not closed.
: Not urgent.
: Not important.

Only the person who set the state can undo it this way -- except
maintainers, who can undo anyone's action (see [[#undoing-updates][Undoing updates]] below).

** Superseding a report

When one report replaces another (a newer patch version, a fresh bug
report capturing the real issue), mark the supersession with either
of two equivalent directives -- they produce the same effect and
differ only by point of view:

- From the *old* report's thread:

  : Superseded-by: <new-message-id@example.com>

- From the *new* report's thread (works in a reply *and* in the
  opening mail of a brand-new bug/patch/request):

  : Supersedes: <old-message-id@example.com>

Message-ids accept three forms: =<id@host>=, bare =id@host=, or the
last path segment of an archive URL (e.g.
=https://list.orgmode.org/orgmode/id@host/=).  Source and target must
be of the same type (both bugs, both patches, or both requests).

To undo: =Not superseded= (from the closed report's thread) or =Not
superseding= (from the replacement's thread).

See the [[#superseding-a-report-1][maintainer section]] for the automatic actions BARK performs
on supersession.

** Marking a report as a duplicate

To mark a report as a duplicate of another, reply with:

: Duplicate-of: <target-message-id@example.com>

Same three message-id forms and type constraints as =Superseded-by:=.
Closes the duplicate with reason =:cancelled= and links it to the
target.  To undo: =Not duplicate.=

Use =Superseded-by:= for "replaced by a newer version" (=:superseded=,
typical for patch v1=>v2); =Duplicate-of:= for "same issue as another
report" (=:cancelled=, typical for duplicated bug reports).

** Cross-referencing reports

To cross-reference another report:

: Related-to: <other-message-id@example.com>

Accepts any pair of reports.  Same message-id forms as
=Superseded-by:= (see above).  Several =Related-to:= lines in one
email post several links.  Works on closed reports.  To undo:
=Not related-to: <other-message-id@example.com>=.

** Resolving a bug or request with a patch
:PROPERTIES:
:CUSTOM_ID: resolving-a-bug-or-request-with-a-patch
:END:

Replying to an open bug or request with a =.patch=/=.diff=
attachment credits you as =Acked= + =Owned= on the *nearest* parent
report.  An existing explicit setter is preserved; opt out with
=Not acked.= / =Not owned.=.

When the reply also produces a separate =:patch= report (labelled
=Re: [PATCH]=, or a =git format-patch= attachment), the patch is
linked to the parent via =:resolves=.  Closing that patch with
=Applied.= / =Fixed.= propagates the closure to the parent (reason
=:resolved=).  Cancelling it retracts the auto-credit; superseding it
transfers ownership to the new author.

The source-level =:patch-triggers? false= flag disables both the
implicit credit and the closure propagation.

** Voting on requests

Requests (=[POLL]=, =[TODO]=, etc.) support voting:

- =+1= or =1+= means "I support"
- =-1= or =1-= means "I don't support"
- =+0=, =0+=, =-0= or =0-= means "I abstain"

* As a maintainer
** Announcements, releases, changes

In addition to bugs, patches, and requests, maintainers can make
general announcements, share a release, or announce an upcoming change
in a future release.

** Events (ICS calendar support)

When an announcement (=[ANN]=) contains an attached =.ics= file or
inline =VCALENDAR= content in the email body, BARK stores the ICS data
alongside the report.  During export, these announcements are collected
into dedicated event feeds:

- Individual =.ics= files are written to =events/<mid-hash>/=.
- Combined ICS calendar files:
  - =events/announcements.ics= --- all announcements with events.
  - =events/announcements-open.ics= --- open only.
  - =events/announcements-closed.ics= --- closed only.
- =events.json=, =events.org=, =events.xml= list open announcements
  with ICS content; =events-closed.*= list closed ones.

Use =[ANN event]= to set the topic to "event" for easier filtering,
but any announcement with ICS content is included regardless of topic.

** Undoing updates

Maintainers can "undo" any update on a report, regardless of who made
it:

: Not acked.
: Not owned.
: Not closed.
: Not urgent.
: Not important.
: No deadline.
: No expiry.
: No topic.
: Not superseded.

All of these can be used by regular users, but only to retract their
*own* actions (see [[#retracting-your-own-updates][Retracting your own updates]] above).  Maintainers
can override any unset, regardless of who posted the original
attribute.

** Setting a deadline

Anyone can set a deadline on a report by writing the following in the
body of a reply:

: Deadline: 2026-03-10.

The date can be in =yyyy-MM-dd= format or a duration (=2d=, =3w=, =1m=,
=1y=), which is resolved relative to today.  An optional trailing
punctuation mark is allowed.  The deadline appears in JSON exports, Org
output (as a proper =DEADLINE:= line), and notification emails.

To remove a deadline:

: No deadline.

** Setting an expiry date

Anyone can set a per-report expiry date.  When the date is reached,
the report is automatically closed with reason "expired", overriding
the source-level expiry rules.

: Expiry: 2026-06-15.
: Expiry: 30d.

Like =Deadline:=, the value can be an ISO date or a duration.  The
expiry date appears in JSON exports (=:expiry=), Org output (=:EXPIRY:=
property), and the HTML index (as a tooltip on the date column).

To automatically expire reports at their deadline, use =:inactive-after
:deadline= in the source-level expiry rules (see [[#report-expiry][report expiry]]).

To remove a per-report expiry:

: No expiry.

** Superseding a report

A =Supersedes:= or =Superseded-by:= directive (see [[#superseding-a-report][the user section]]
for syntax and message-id forms) triggers three automatic actions:

1. Poses a =:supersedes= qualified relation (=:rel/from= = the closed
   report, =:rel/to= = the replacement) and a symmetric =:related-to=
   audit link.
2. Closes the old report with close-reason =:superseded=.
3. Links the two reports as related (bidirectional, kept on undo).

In the index, superseded reports appear struck through (like canceled
reports) with an "S" status flag; the subject tooltip shows the
replacement's title.

Last-write-wins on direction: if a later directive flips the direction
(e.g. =Supersedes: <X>= posed at t1, then =Superseded-by: <X>= posed
at t2 on the same report), the second pose retracts the first,
reopens the previously-closed report, and applies the new direction.

Undo scope: =Not superseded= and =Not superseding= can be issued by
the original setter or by any maintainer.  Either retracts the
relation, reopens the closed report, and clears the close-reason; the
=:related-to= link is kept.

*** Automatic supersession of patches

When a new patch report is created in a thread where an earlier open
patch report shares the same base subject (ignoring =Re:= / =Fwd:=
prefixes and =[TAG]= brackets), the new report automatically supersedes
the previous one.  This covers re-sent patches without explicit version
numbers.

For example:

#+begin_example
[PATCH] A new feature          : patch report (1)
  Re: [PATCH] A new feature    : patch report (2), supersedes (1)
    Re: [PATCH] A new feature  : patch report (3), supersedes (2)
#+end_example

Only the most recent patch (3) remains open.

The reply must itself qualify as a patch report (=Re: [PATCH]= with
an attached patch, or a real =git format-patch= attachment) -- a bare
=Re:= without an attached patch creates no report and supersedes
nothing.

Patches with explicit version numbers (=[PATCH v2]=) are handled by
a separate mechanism that matches on version and topic.

** Acting as an update proxy

Maintainers can also write directly to the BARK inbox to act as
"proxies" and update a report as if they were users:

: Acked-by: a-user@example.com
: Owned-by: a-user@example.com
: Closed-by: a-user@example.com
: Urgent-by: a-user@example.com
: Important-by: a-user@example.com

The RFC 5322 =Display Name <addr>= format is also accepted:

: Owned-by: A User <a-user@example.com>

** Managing roles and permissions

Here is how the permissions work:

- There is only one lead maintainer per source.
- Maintainers can promote other users to maintainers.
- Only the lead maintainer can demote maintainers as users.

Roles and permissions are set by writing to the BARK inbox:

#+begin_example
Add maintainer: dev@example.com        (any maintainer)
Remove maintainer: dev@example.com     (lead maintainer only)
#+end_example

The RFC 5322 =Display Name <addr>= format is also accepted:

#+begin_example
Add maintainer: Dev User <dev@example.com>
#+end_example

All state-changing actions (commands, role controls) must be sent
through the source's public channel (mailing list, alias). This
ensures that anyone running BARK on the same source sees the same
state.  Notification preferences are personal and can be sent
privately.

* Report types

Reports are detected from email subject labels:

| Tag                               | Type         |
|-----------------------------------+--------------|
| =[BUG <topic>]=                     | bug          |
| =[PATCH <topic> <version> <n/m>]=   | patch        |
| =[POLL <topic>]= or =[TODO <topic>]=  | request      |
| =[ANN <topic>]=                     | announcement |
| =[REL <topic> <version>]=           | release      |
| =[CHG <topic> <version>]=           | change       |

Long-form aliases are also accepted: =[ANNOUNCEMENT]=, =[RELEASE]=,
=[CHANGE]=.

Labels are case-sensitive and require whitespace (or end of subject)
after the closing =]=.  Malformed labels are ignored.

Announcements, releases and changes require maintainer permission.

All =<…>= parts are optional and positional. For release and change, a
single value is interpreted as =<version>=: =[REL 2.0]= sets version to
"2.0". Use both for topic and version: =[REL parser 2.0]=. For patch,
=<version>= is a =v\d+= token (e.g. =v2=) and =<n/m>= is a sequence marker
(e.g. =3/5=).

When a =[REL <version>]= report is created, any open =[CHG <version>]=
reports with the same version are automatically closed, and reports
will be marked as related.

** Patch series

When patches include a sequence marker (=<n/m>=), BARK groups them into
a series. A cover letter (=0/m=) or a new =1/m= patch from the same sender
and topic automatically closes the previous series and starts a fresh
one. This allows version superseding: sending =[PATCH parser v2 0/3]=
closes the earlier =v1= series for that topic.

** Customising subject labels

The subject labels in the table above are the built-in defaults. You
can override them globally or per source in =config.edn= via =:labels=.
Specify only the types you want to change; unspecified types keep
their defaults.

#+begin_src edn
;; Global override (applies to all sources)
:labels {:bug     ["BUG" "DEFECT"]
         :request ["POLL" "FR" "TODO" "RFE"]}
#+end_src

#+begin_src edn
;; Per-source override (inside a source map)
{:name "my-list"
 :labels {:announcement ["ANN" "NEWS"]}}
#+end_src

Per-source settings take precedence over the global =:labels=, which in
turn take precedence over the built-in defaults.

* Commands

State changes are detected by command keywords within the body of a
response down the thread, at the beginning of the line, followed by
punctuation (=.= =,= =;= =:= =?= =!=), whitespace, or end of line. Exception:
=Urgent= and =Important= only accept punctuation or end of line (see
[[#priority-commands][priority commands]]).

Directives that take a parameter (=Topic:=, =Deadline:=, =Expiry:=,
=Acked-by:=, =Owned-by:=, =Closed-by:=, =Urgent-by:=, =Important-by:=,
=Superseded-by:=) require **at least one whitespace character between
the colon and the value**.  =Topic: parser= is recognised; =Topic:parser=
(no space) is silently ignored.

** Status commands

| Command keyword                         | Effect on report  |
|-----------------------------------------+-------------------|
| =Acked= =Confirmed= =Approved=                | acked             |
| =Owned=                                   | owned             |
| =Canceled= =Cancelled=                      | closed (canceled) |
| =Expired=                                 | closed (expired)  |
| =Resolved= =Applied= =Fixed= =Closed= =Completed= | closed (resolved) |

All reports can be in a combination of three states:

- *Acked* --- someone took the next sensible action (confirmed a bug, reviewed a patch, approved a request).
- *Owned* --- someone claimed ownership of this report.
- *Closed* --- the report is resolved, canceled, or expired.

When the status is represented as a number, it is computed like this:

| (Un)acked  | (0)1 |
| (Un)owned  | (0)2 |
| (Un)closed | (4)0 |

So an acked, unowned and open report is =1+0+4 = 5=.

Note that only bugs, patches, and requests support the acked and
owned states. Announcements, releases, and changes cannot be acked or
owned, but they can still be marked urgent or important and closed.

** Priority commands

| Command keyword | Effect on report  |
|-----------------+-------------------|
| =Urgent.=         | Mark as urgent    |
| =Important.=      | Mark as important |

Unlike other triggers, =Urgent= and =Important= require punctuation
(=.= =,= =;= =:= =?= =!=) or end of line --- a bare space is not
accepted, to avoid false positives from ordinary prose.

These values are used to calculate the "priority" sum:

| (Un)important | (0)1 |
| (Un)urgent    | (0)2 |

So an important and urgent report is =1+2 = 3=.

** Multiple commands

You can use multiple keywords in the same email, one per line.

: From: x@y.z
: Date: Thu, 19 Mar 2026 16:45:00 +0100
: Subject: [BUG] BARK is too good!
: 
: > I have too much free time now.
: 
: Confirmed.
: Urgent.
: Important.

** Customising commands

You can customize command keywords globally or per source.

*** Overriding words, permissions, and report types

Each entry is a map with any of =:words=, =:scope=, =:report-types=
(at least one must be present):

#+begin_src edn
:commands {:closed   {:words ["Canceled" "Fixed" "Wontfix"]}
           :acked    {:words ["Approved" "LGTM"]
                      :scope :maintainer}               ;; Restrict to maintainers
           :deadline {:report-types
                      #{:bug :patch :request :change}}  ;; Widen to changes
           :unclosed {:scope :setter-or-maintainer}}    ;; Override scope only
#+end_src

- =:scope= overrides the default permission for that command. Possible
  values:
  - =:user= -- anyone
  - =:maintainer= -- maintainer only
  - =:setter-or-maintainer= -- the address that previously set the
    attribute, or any maintainer (maintainers keep their administrative
    override)

  =:setter-or-maintainer= is only valid on unset directives whose
  target attribute is tracked by a ref to the pose-email: =:unacked=,
  =:unowned=, =:unclosed=, =:unurgent=, =:unimportant=, =:untopic=,
  =:undeadline=, =:unexpiry=, =:unsuperseded=, =:unsupersedes=,
  =:unduplicate=.  =bb test-config= rejects this scope on any other
  command.
- =:report-types= replaces the default set of report types the command
  applies to. When absent, the registry default is used.
- Any command ID from the table below can be overridden, both triggers
  and directives.
- Controls (role and notify) cannot be overridden.

Per-source settings take precedence over the global =:commands=, which
in turn take precedence over the built-in defaults.

*** Syntax mode: =:loose= vs =:strict=

The =:command-syntax= key (=:loose= default, =:strict= opt-in) controls
whether Bark instructions must be prefixed with =!=.  =:strict= eliminates
false positives on common English words like "Done.", "Closed." or
"Applied." that appear naturally in conversation.

| Form             | Loose                  | Strict                 |
|------------------+------------------------+------------------------|
| Trigger          | =Closed.= / =!Closed.=     | =!Closed.=               |
| Negative trigger | =Not acked= / =!Not acked= | =!Not acked=             |
| =-by= directive    | =Acked-by: a@b.c=        | =!Acked-by: a@b.c=       |
| Date directive   | =Deadline: 2026-06-01=   | =!Deadline: 2026-06-01=  |
| Topic            | =Topic: event=           | =!Topic: event=          |
| Supersede        | =Superseded-by: <mid>=   | =!Superseded-by: <mid>=  |
| Supersede (sym.) | =Supersedes: <mid>=      | =!Supersedes: <mid>=     |
| Role control     | =Add maintainer: a@b.c=  | =!Add maintainer: a@b.c= |
| Notify           | =Notify: on=             | =!Notify: on=            |

Set globally or per source (per-source wins):

#+begin_src edn
:command-syntax :strict
#+end_src

**** Replaying archives under a different convention

When a source's vocabulary or syntax mode has changed over time (a
list that tightened from =:loose= to =:strict=, or accepted =Done.=
only during a specific era), declare the history inline with =:periods=
(see [[#source-periods][Source periods]]).  Each period carries its own overrides for
=:commands=, =:command-syntax= and =:maintainers=; the core resolves
the effective config at each email's date without any per-email
timeline logic.

** All controls

/Controls/ manage roles and notification preferences.
Role controls must be sent via the source's public channel.
Notification controls can be sent privately.

| ID     | Syntax / Words                     | Permission      | Channel |
|--------+------------------------------------+-----------------+---------|
| notify | =Notify: on= / =off= / =d:7 p:2 s:4 ...= | maintainer      | any     |
| role   | =Add maintainer: addr@host=          | maintainer      | public  |
| role   | =Remove maintainer: addr@host=       | lead maintainer | public  |

* Exploring reports

The BARK instance can expose reports as HTML, JSON, Org and RSS.

** Exported pages and feeds

Running =bb export all= generates, for each source:

- HTML pages: =index.html= (reports table), =stats.html= (charts),
  =docs.html= (user docs).
- Full exports: =all.json=, =all.org=, =all.xml=.
- Per-type feeds: =bugs.json=, =patches.xml=, =requests.org=, etc.
- =votes.json= --- per-report vote details (see below).
- =patches/= --- attached and inline patch files.
- =text/<mid-hash>/= --- =text/plain= and =text/x-log= attachments
  (backtraces, log files).
- =events/<mid-hash>/= --- =.ics= attachments from announcements;
  combined feeds at =events/announcements{,-open,-closed}.ics=
  aggregate VEVENT blocks for subscription.
- =events.{json,org,xml}= and =events-closed.{json,org,xml}= ---
  open/closed announcements carrying =.ics= or inline VCALENDAR content.

RSS feeds contain up to 50 items, most recent first.  Export is
incremental (only sources modified since the last export are
re-generated); use =--force= to bypass.

Single-format export: =bb export {json|rss|org|html|stats|text|events}=.

| Flag                  | Purpose                                                  | Configurable |
|-----------------------+----------------------------------------------------------+--------------|
| =-n <source>=           | restrict to one source                                   | --           |
| =-p <N>=                | filter by minimum priority                               | --           |
| =-s <N>=                | filter by minimum status                                 | --           |
| =--page-size <N>=       | paginate HTML report table (client-side rendering)       | CLI only     |
| =--closed-retention=    | exclude reports closed before given ISO date or duration | CLI only     |
| =--topics-filter=       | restrict to topics (comma-separated, case-insensitive)   | per source   |
| =--force=               | force a full re-export                                   | CLI only     |

Durations accept =Nd=, =Nw=, =Nm=, =Ny= (e.g. =--closed-retention 1y=
keeps reports closed within the last 12 months).

** Vote transparency

Votes on =request= reports are stored as individual entities, each
recording who voted and in which email. The export produces a
=votes.json= file for each source so that anyone can audit votes:

#+begin_src json
{
  "<11@test.org>": {
    "+1": [{"voter": "alice@example.org", "message-id": "<12@test.org>"}],
    "-1": [{"voter": "bob@example.org",   "message-id": "<13@test.org>"}],
    "0":  []
  }
}
#+end_src

Each voter can only vote once per report (first vote wins). Summary
counts (=votes=, =votes-up=, =votes-down=, =votes-null=) are still included in
the JSON report objects for display convenience, derived from these
entities at export time.

* Notifications

BARK can send periodic email notifications to maintainers with a
summary of open reports. Notifications are never sent to regular
users.

Notifications require SMTP configuration (see [[#config][Config]]) and are sent via
=bb notify=, typically from a cron job. Use =bb notify --dry-run= to
preview without sending. Each notification email contains two
sections: open bugs/patches/requests owned by the recipient, and all
unacked & unowned bugs/patches/requests by anyone.

** (Un)subscribing

Maintainers are subscribed by default when the daemon runs for the
first time. To unsubscribe, send an email to the BARK inbox with this
body:

#+begin_example
Notify: off
#+end_example

To re-subscribe:

#+begin_example
Notify: on
#+end_example

** Setting preferences

Notification preferences are set via the same =Notify:= control.
Parameters can be combined on a single line:

| Parameter | Description                        | Default |
|-----------+------------------------------------+---------|
| =d:N=       | Receive notifications every N days |      30 |
| =p:N=       | Minimum priority (0--3)            |       1 |
| =s:N=       | Minimum status (0--7)              |       1 |
| =m:<match>= | Restrict to subject <match>        |         |
| =t:<topic>= | Restrict to topic <topic>          |         |

Examples:

#+begin_example
Notify: d:7                 -- every 7 days
Notify: d:1                 -- daily
Notify: p:1                 -- only important reports
Notify: d:3 s:4 p:2         -- every 3 days, only open reports with priority >= 2
#+end_example

Unlike role controls, =Notify:= controls are personal and accepted on
any channel (private email or mailing list).

* Config

BARK is configured via a =config.edn= file. Use =bb test-config= to
validate it.

** Minimal example

#+begin_src edn
{:mailbox {:type     :imap
           :host     "imap.example.com"
           :port     993
           :ssl      true
           :user     "imap-login@example.com"
           :password "secret"
           :folder   "INBOX"}

 :sources [{:name        "my-list"
            :list        "my-list.example.org"
            :maintainers ["lead@example.org"]}]}
#+end_src

=:db=, =:logging= and =:ingest= are optional; omitted they default to
=:db {:path "data/bark-db"}=, stderr-only logging at =:info= level,
and =:ingest {:fetch {:limit 50}}=.  See =config.edn.example= for the full
annotated reference.

BARK also reads Maildir folders.  Point =:path= at the parent
directory that contains =cur/=, =new/= and =tmp/=; =:folder= selects
the subfolder to read.  =--watch= on a Maildir source uses filesystem
events (no polling).

#+begin_src edn
{:mailbox {:type   :maildir
           :path   "/home/me/Mail"
           :folder "INBOX"}
 :sources [{:name "my-list" :list "my-list.example.org"}]}
#+end_src

** Source types and matching

Each source has exactly one type key that determines how emails are
matched:

- =:list= --- matches the =List-Id= header (bare identifier, e.g.
  ="my-list.example.org"=).  Emails are detected as list mail when
  =List-Id= or =X-BeenThere= is present.
- =:alias= --- matches =X-Original-To=, =Envelope-To=, =X-Envelope-To=, or
  =Delivered-To=.  Emails are detected as alias mail when the original
  recipient (from these headers) differs from =To=/=Cc=, or when multiple
  distinct =Delivered-To= values are present.
- =:to= --- matches =Delivered-To=.  This is for a dedicated mailbox
  where all emails are delivered directly.

Emails that don't match any source are not stored.

** Source options

| Key                    | Description                                                                  |
|------------------------+------------------------------------------------------------------------------|
| =:name=                  | Source identifier (required)                                                 |
| =:list= / =:alias= / =:to=   | Exactly one (determines source type and header to match)                     |
| =:maintainers=           | Initial maintainers as a vector of email strings, e.g. =["dev@example.org"]=   |
|                        | The first entry is the lead maintainer (see [[#managing-roles-and-permissions][Managing roles and permissions]])  |
| =:list-archive=          | URL of the list archive (shown in HTML reports)                              |
| =:archive-format-string= | URL template for message-ids (=%s= is replaced), used when the                 |
|                        | =Archived-At= header is absent                                                 |
| =:base-url=              | Base URL where this source's public directory is served                      |
| =:labels=                | Per-source label overrides (see [[#customising-subject-labels][customising subject labels]])                  |
| =:commands=              | Per-source command overrides (see [[#customising-commands][customising commands]])                      |
| =:report-types=          | Restrict detected and exported types, e.g. =#{:bug :patch}=                    |
| =:export-formats=        | Output formats, e.g. =["json" "rss"]=  (default: =["json" "org" "rss"]=)         |
| =:expiry=                | Auto-close rules per report type (see below)                                 |
| =:notifications=         | ={:enabled false}= to silence notifications for this source (default: enabled) |
| =:awaiting-delay=        | Duration before flagging "awaiting reply", e.g. ="14d"= (default: 14 days)     |
| =:periods=               | Time-windowed overrides for maintainers/commands (see [[#source-periods][Source periods]])        |

** Source periods

When a source's vocabulary or maintainer list has evolved over time,
declare the history inline with =:periods= --- a vector of time-windowed
overrides.  Each entry may declare =:start= / =:end= (ISO =yyyy-MM-dd=)
plus any of =:maintainers=, =:commands=, =:command-syntax=, =:labels=.
Fields omitted in a period inherit from the source level, which
represents the current state.

#+begin_src edn
{:name "orgmode"
 :list "emacs-orgmode@gnu.org"
 :maintainers ["current-lead@example.org"]    ;; default + current era
 :periods
 [{:end "2020-01-01"
   :maintainers ["old-lead@example.org"]
   :commands    {:closed {:words ["Done" "Fixed"]}}}
  {:start "2020-01-01" :end "2024-01-01"
   :maintainers ["mid-lead@example.org" "co@example.org"]}
  {:start "2024-01-01"                         ;; last era, no :end
   :maintainers ["current-lead@example.org"]}]}
#+end_src

Rules:
- Periods must be /contiguous/: =:end= of era /N/ equals =:start= of era /N+1/.
- Only the /first/ period may omit =:start= (unbounded past).
- Only the /last/ period may omit =:end= (still active).
- =bb test-config= validates the periods and rejects gaps or overlaps.
- Maintainer tenure at each boundary is computed via /sync/:
  declared maintainers missing at the boundary are added,
  previously-active maintainers absent from the declared list are
  closed at the boundary's =:start=.
- =Add/Remove maintainer:= directives in emails continue to mutate
  tenures in real time /between/ boundaries.
- Sync is /idempotent/: re-running on an existing DB never duplicates
  tenures and does not reinstate maintainers closed by a past mail
  directive.  To replay from scratch (wiping mail-directive history
  along with everything else), run =clj -M:run -- --fresh=.

** Report expiry

Any report type can be automatically closed when its age and state
match configured rules.  The close reason is set to "expired".

Each entry under =:expiry= maps a report type keyword to a rule map:

| Rule key        | Type                      | Description                                             |
|-----------------+---------------------------+---------------------------------------------------------|
| =:inactive-after= | string / date / =:deadline= | Duration ("30d"), ISO date ("2026-06-01"), or =:deadline= |
| =:max-status=     | integer                   | Don't expire if activity score > this value (0--3)      |
| =:max-priority=   | integer                   | Don't expire if priority > this value (0--3)            |

All rules are conjunctive: a report is only expired when *all*
conditions are met.  Only =:inactive-after= is required; the others are
optional filters.

| =:inactive-after= value | Trigger                                                                |
|-----------------------+------------------------------------------------------------------------|
| Duration (e.g. =30d=)   | Last email in the thread is older than the duration (any reply resets) |
| ISO date              | The fixed date has passed, regardless of activity                      |
| =:deadline=             | The report's deadline is in the past (no deadline => never expires)    |

The =:max-status= value uses an activity score that only counts acked
and owned (since expiry candidates are always open reports):

| Score | Meaning          |
|-------+------------------|
|     0 | unacked, unowned |
|     1 | acked            |
|     2 | owned            |
|     3 | acked + owned    |

#+begin_src edn
:expiry {:announcement {:inactive-after "30d"}
         :release      {:inactive-after "6w"}
         :change       {:inactive-after "3m"}
         :bug          {:inactive-after "1000d"
                        :max-status 0      ;; only open, unacked, unowned
                        :max-priority 0}   ;; only non-urgent, non-important
         :request      {:inactive-after "1000d"
                        :max-status 0}}
#+end_src

This can be set globally or per source (per-source takes precedence).

In addition to these source-level rules, maintainers can set a
per-report expiry date using the =Expiry:= directive (see [[#report-expiry][report
expiry]]). A per-report expiry overrides the source-level rules: if a
report has an explicit expiry date, only that date is checked.

** Ingestion

#+begin_src edn
:ingest {:fetch    {:limit 50}    ;; or {:since "30d"} or {:start "…" :end "…"}
         :max-size 1048576}       ;; skip emails > 1 MB (optional)
#+end_src

- =:fetch= -- first-run fetch window (no watermark yet).  Exactly one
  of three disjoint map shapes (no key mixing, empty map rejected);
  default is ={:limit 50}=:

  | Config form                      | CLI shortcut       | Meaning                                                                           |
  |----------------------------------+--------------------+-----------------------------------------------------------------------------------|
  | ={:limit N}=                       | =--fetch 50=         | Latest N messages (positive integer)                                              |
  | ={:since "Nd"}=                    | =--fetch 30d=        | Relative duration from now (=Nd=, =Nw=, =Nm=, =Ny=)                                       |
  | ={:start "yyyy-MM-dd" :end "..."}= | =--fetch 2020-01-01= | Absolute half-open window =[start, end)=; both keys optional, at least one required |

- =:max-size= -- skip emails larger than N bytes.  No limit by default.

Text content of =.patch=, =.diff=, =.ics=, =text/plain= and =text/x-log=
attachments is extracted and stored in the database. Attachments
larger than 1 MB (1,048,576 characters) are skipped with a warning --
only metadata (filename, size, content-type) is kept. Override the
limit with =:max-attachment-size= in the =:ingest= config section.

** Maintenance

Run =bb maintenance= when the daemon is stopped.

#+begin_src shell
bb maintenance                  # dry run, show orphan counts
bb maintenance --delete         # actually delete orphan emails
bb maintenance --verbose        # list individual orphan message-ids
bb maintenance --failures       # list recent command failures recorded
                                # for maintainers (denied actions, bad
                                # syntax, etc.)
bb maintenance --retention 6m   # override default orphan retention
                                # (90 days). Accepts "30d", "6m", "1y"
                                # or an ISO date.
bb maintenance -n my-source     # scope to a single source
#+end_src

An orphan email is one not referenced by any report and not sent by a
maintainer.

** Running BARK in production

Two practical ways to keep BARK running:

- *Watch mode under systemd* -- the daemon stays up, reacts to IMAP IDLE
  or Maildir filesystem events, reconnects on failure. A ready-to-edit
  unit file lives in =docs/deploy/bark.service=. Install to
  =/etc/systemd/system/bark.service= (root) or =~/.config/systemd/user/=
  (user), then =systemctl [--user] daemon-reload && systemctl [--user]
  enable --now bark=.

- *Batch mode under cron* -- =clj -M:run= is a one-shot: connect, fetch
  new mail since the watermark, digest, expire, exit. Chain =bb export=
  and =bb notify= after it. An example crontab lives in
  =docs/deploy/crontab.example=.

Both modes can be backed by an uberjar instead of =clj -M:run= to
avoid paying the Clojure startup cost on every invocation; see the
*Quick start* section of =README.org=.

** Rebuilding history

Historical evolution (vocabulary, syntax, maintainers) is declared
per-source via =:periods= entries --- see [[#source-periods][Source periods]] for the full
format and rules. At startup, =bark= materialises the tenure history by
syncing at each period boundary, and resolves the effective config for
every email based on its date.

To replay from scratch after editing periods (or after any config
change you want reflected retroactively), wipe the DB:

#+begin_src shell
clj -M:run -- --fresh   # interactive confirm, then full replay
#+end_src

=bb test-config= validates the =:periods= on each source: contiguity, ISO
date format, =:start= strictly before =:end=.

* Appendix 1: workflow examples

** Patch review cycle

A contributor submits a patch series:

: From: carol@dev.org
: Subject: [PATCH parser v1 0/2] Refactor tokenizer
: 
: Cover letter: this series splits the tokenizer into two passes.

: From: carol@dev.org
: Subject: [PATCH parser v1 1/2] Extract lexer phase
: 
: <inline patch>

: From: carol@dev.org
: Subject: [PATCH parser v1 2/2] Add second pass
: 
: <inline patch>

BARK creates a patch series (3 emails, cover + 2 patches).  The
maintainer reviews and asks for changes:

: From: eve@project.org
: Subject: Re: [PATCH parser v1 1/2] Extract lexer phase
: 
: > <inline patch>
: 
: The naming is confusing, can you rename foo to bar?

Carol resubmits as v2:

: From: carol@dev.org
: Subject: [PATCH parser v2 0/2] Refactor tokenizer
: 
: v2: renamed foo to bar as requested.

BARK automatically closes the v1 series and opens a new v2 series.
The maintainer applies:

: From: eve@project.org
: Subject: Re: [PATCH parser v2 0/2] Refactor tokenizer
: 
: Applied, thanks!

The v2 series is now closed (resolved).

** Maintainer triage

A bug comes in with no response for a while.  The maintainer triages
by replying to the list:

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Re: [BUG] Crash on startup
: 
: Confirmed.
: Owned.
: Urgent.

Later, the fix lands:

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Re: [BUG] Crash on startup
: 
: Fixed in commit abc123, thanks for reporting!

** Role management

Any maintainer adds a new maintainer (via the list):

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Role update
:
: Add maintainer: newdev@project.org

Only the lead maintainer can =Remove maintainer:=.

** Automatic expiry and override

With this config:

#+begin_src edn
:expiry {:bug {:inactive-after "90d" :max-status 0}}
#+end_src

A bug whose last email is 91 days ago, still unacked and unowned, is
automatically closed with reason "expired" on the next expiry run.

A maintainer notices a legitimately old bug that should stay open and
sets a far-future expiry to protect it:

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Re: [BUG] Legacy encoding issue
: 
: This is still relevant, keeping it open.
: No expiry.
: Owned.

By marking the bug as owned, it no longer matches =:max-status 0= and
won't be expired by the rule.  =No expiry.= clears any per-report expiry
date that may have been set previously.
