* BARK! Another Report Keeper

BARK monitors a mailbox and converts incoming emails into reports.
Subsequent emails in the same thread can update the status of that
report using predefined trigger keywords. Admins and maintainers can
update reports by writing directly to the monitored inbox, manage
roles, and receive periodic digest emails.

* As a user

** Bug, Patch, Request

As a user, you can report bugs, propose patches and make other
requests:

- You create a bug report by adding =[BUG]= to the subject.
- You send a patch by adding an inline or attached patch.
- You can also create a =[POLL]=, share a feature request =[FR]= or a
  =[TODO]=.

See below the list of [[#report-types][report types]].

** Setting a topic

Topics can be set in two ways:

- *Inside the label*: =[BUG parser]= sets topic to "parser".
- *Colon prefix after the label*: =[BUG] parser: crash on empty input=
  also sets topic to "parser" (the first colon-delimited segment after
  the closing bracket).

A maintainer can also change the topic of an existing report by
replying with:

: Topic: new-topic.

** Updating reports

State changes occur when a reply in the same thread contains a
case-sensitive trigger keyword at the start of a line, followed by a
punctuation mark (=.= =,= =;= =:=). For example, a reply to a bug report with
a line starting with =Confirmed.= marks the bug as "acked"; a reply to a
patch with a line starting with =Applied.= marks the patch as "closed".

See the [[#trigger-keywords][trigger keywords]] below for the full list.

** Voting on requests

Requests (=[POLL]=, =[FR]=, =[TODO]=, etc.) support voting:

- =+1= or =1+= means "I support"
- =-1= or =1-= means "I don't support"
- =+0=, =0+=, =-0= or =0-= means "I abstain"

* As a maintainer or admin
** Announcements, releases, changes

In addition to bugs, patches, and requests, maintainers can make
general announcements, share a release, or announce an upcoming change
in a future release.

** Undoing updates

Maintainers can also "undo" an update:

: Unacked.
: Unowned.
: Unclosed.
: Unurgent.
: Unimportant.
: Undeadline.

** Setting a deadline

Maintainers can set a deadline on a report by writing the following
in the body of a reply:

: Deadline: 2026-03-10.

The date must be in =yyyy-MM-dd= format, followed by a punctuation
mark.  The deadline appears in JSON exports, Org output (as a proper
=DEADLINE:= line), and notification emails.

To remove a deadline:

: Undeadline.

** Updating offlist

Also, maintainers can write directly to the watched inbox to update a
report without notifying the list.

For example, the maintainer can clean up old issues by marking them as
=Cancelled= in the body of a reply sent to the monitored inbox, rather
than to the entire list. This is also useful for reclassifying emails:
if someone forgot the =[BUG]= prefix, a maintainer can edit the subject
and resend the email to the BARK inbox.

** Acting as an update proxy

Maintainers can also write directly to the BARK inbox to act as
"proxies" and update a report as if they were users:

: Acked-by: a-user@example.com
: Owned-by: a-user@example.com
: Closed-by: a-user@example.com
: Urgent-by: a-user@example.com
: Important-by: a-user@example.com

** Managing roles and permissions

Here is how the permissions work:

- There is only one admin per source.
- The admin and maintainers can promote users as maintainers.
- The admin can demote maintainers as users.
- The admin and maintainers can ignore users.
- The admin can "unignore" users.

Roles and permissions are set by writing to the BARK inbox:

#+begin_example
Add maintainer: dev@example.com        (admin or maintainer)
Remove maintainer: dev@example.com     (admin only)
Ignore: spammer@example.com            (admin or maintainer)
Unignore: user@example.com             (admin only)
#+end_example

* Report types
  :PROPERTIES:
  :CUSTOM_ID: report-types
  :END:

Reports are detected from email subject labels:

| Tag                                                 | Type         |
|-----------------------------------------------------+--------------|
| =[BUG <topic>]=                                       | bug          |
| =[PATCH <topic> <version> <n/m>]=                     | patch        |
| =[POLL <topic>]= =[FR <topic>]= =[TODO <topic>]=          | request      |
| =[ANN <topic>]= =[ANNOUNCEMENT <topic>]=                | announcement |
| =[REL <topic> <version>]= =[RELEASE <topic> <version>]= | release      |
| =[CHG <topic> <version>]= =[CHANGE <topic> <version>]=  | change       |

All =<…>= parts are optional and positional.  For release and change, a
single value is interpreted as =<version>=: =[REL 2.0]= sets version to
"2.0".  Use both for topic and version: =[REL parser 2.0]=.  For patch,
=<version>= is a =v\d+= token (e.g. =v2=) and =<n/m>= is a sequence marker
(e.g. =3/5=).

When a =[REL <version>]= report is created, any open =[CHG <version>]=
reports with the same version are automatically closed.

Announcements, releases and changes require maintainer permission.

** Patch series

When patches include a sequence marker (=<n/m>=), BARK groups them
into a series.  A cover letter (=0/m=) or a new =1/m= patch from the
same sender and topic automatically closes the previous series and
starts a fresh one.  This allows version superseding: sending
=[PATCH parser v2 0/3]= closes the earlier =v1= series for that topic.

** Customising subject labels
   :PROPERTIES:
   :CUSTOM_ID: customising-subject-labels
   :END:

The subject labels in the table above are the built-in defaults. You
can override them globally or per source in =config.edn= via =:labels=.
Specify only the types you want to change; unspecified types keep
their defaults.

#+begin_src edn
;; Global override (applies to all sources)
:labels {:bug     ["BUG" "DEFECT"]
         :request ["POLL" "FR" "TODO" "RFE"]}
#+end_src

#+begin_src edn
;; Per-source override (inside a source map)
{:name "my-list"
 :labels {:announcement ["ANN" "NEWS"]}}
#+end_src

Per-source settings take precedence over the global =:labels=, which in
turn take precedence over the built-in defaults.

* Trigger keywords
  :PROPERTIES:
  :CUSTOM_ID: trigger-keywords
  :END:

State changes are detected by trigger keywords within the body of a
response down the thread, at the beginning of the line, followed by a
punctuation mark (=.= =,= =;= =:=):

** Status triggers

| Effect on report  | Trigger keyword                    |
|-------------------+------------------------------------|
| acked             | =Acked= =Confirmed= =Reviewed= =Approved=  |
| owned             | =Owned= =Handled= =Assigned=             |
| closed (canceled) | =Canceled= =Cancelled=                 |
| closed (expired)  | =Expired=                            |
| closed (resolved) | =Resolved= =Applied= =Done= =Fixed= =Closed= |

** Priority triggers

| Effect on report | Trigger keyword |
|------------------+-----------------|
| urgent           | =Urgent=          |
| important        | =Important=       |

Priority is never set directly: it is computed as the sum of
important (=+1=) and urgent (=+2=), giving a value between 0 and 3.

You can use multiple keywords in the same email, one per line.

All trigger keywords work on all report types.  However, only bugs,
patches, and requests support the acked, owned, urgent, and important
states.  Announcements, releases, and changes can only be closed.

** Report statuses and priority

All reports can be in a combination of three states:

- *Acked* --- someone took the next sensible action (confirmed a bug, reviewed a patch, approved a request).
- *Owned* --- someone claimed ownership of this report.
- *Closed* --- the report is resolved, canceled, or expired.

** Status (as number)

When the status is represented as a numeric value, it is computed like
this:

| (Un)acked  | (0)1 |
| (Un)owned  | (0)2 |
| (Un)closed | (4)0 |

So an acked, unowned and open report is =1+0+4 = 5=.

** Priority (as number)

| (Un)important | (0)1 |
| (Un)urgent    | (0)2 |

So an important and urgent report is =1+2 = 3=.

** Customising trigger keywords
   :PROPERTIES:
   :CUSTOM_ID: customising-trigger-keywords
   :END:

You can customize trigger keywords globally or per source:

 : :triggers {:closed ["Canceled" "Fixed" "Resolved" "Wontfix"]
 :            :acked  ["Approved" "Reviewed" "LGTM"]}

* Exploring reports

The BARK instance can expose reports as HTML, JSON, Org and RSS.

** Exported pages and feeds

Running =bb export all= generates, for each source:

- =index.html= --- the main reports table (filterable, sortable).
- =stats.html= --- report statistics and charts.
- =docs.html= --- a user-facing documentation page (from =docs-tpl.org=).
- =all.json=, =all.org=, =all.xml= --- full exports in JSON, Org and RSS.
- Per-type feeds: =bugs.json=, =patches.xml=, etc.
- =patches/= --- a directory with attached and inline patch files.

RSS feeds contain up to 50 items, most recent first.

Export is incremental: only sources modified since the last export are
re-generated.  Use =bb export all --all= to force a full re-export.

You can also export a single format:

: bb export json
: bb export rss
: bb export org
: bb export html
: bb export stats

Use =-n <source>= to restrict to one source, =-p <N>= to filter by
minimum priority, and =-s <N>= to filter by minimum status.

** Browsing BARK reports online

A web interface lets you navigate BARK reports.

The search field has a minimal syntax:

| Long form                   | Short | Explanation                                           |
|-----------------------------+-------+-------------------------------------------------------|
| from:me@example.org         | f:    | Reports from me@example.org                           |
| acked:me@example.org        | a:    | Reports acked by me@example.org                       |
| owned:me@example.org        | o:    | Reports owned by me@example.org                       |
| closed:me@example.org       | c:    | Reports closed by me@example.org                      |
| urgent:me@example.org       | u:    | Reports marked urgent by me@example.org               |
| important:me@example.org    | i:    | Reports marked important by me@example.org            |
| subject:match               | s:    | Reports matching subject                              |
| topic:match                 | t:    | Reports matching topic                                |
| priority:[0-4]              | p:    | Reports matching priority level 0 to 4                |
| mid:<messageid>             | m:    | Report with message-id <messageid>                    |
| date:3d..                   | d:    | Reports from 3 days ago                               |
| date:2023-01-01..2023-12-31 | d:    | Reports from 2023-01-01 to 2023-12-31                 |
| match1 \vert match2             |       | Reports matching "match1" or "match2"                 |
| *                           |       | Wildcard for from/acked/owned/closed/urgent/important |

** The =bone= CLI tool, =gnus-bone.el= and =notmuch-bone.el=

[[https://codeberg.org/bzg/bone][bone]] lets you browse and filter BARK reports interactively from the
terminal.

[[https://codeberg.org/bzg/gnus-bone][gnus-bone.el]] lets you explore BARK reports from within [[https://gnus.org/][Emacs Gnus]].

[[https://codeberg.org/bzg/notmuch-bone][notmuch-bone.el]] provides the same integration for [[https://notmuchmail.org/][notmuch]].

* Notifications

BARK can send periodic email notifications to admins and maintainers
with a summary of open reports. Notifications are never sent to
regular users.

Notifications require SMTP configuration (see [[#config][Config]]) and are sent via
=bb notify=, typically from a cron job.  Use =bb notify --dry-run= to
preview without sending.  Each notification email contains two
sections: open bugs/patches/requests owned by the recipient, and all
unacked & unowned bugs/patches/requests by anyone.

** (Un)subscribing

Admins and maintainers are subscribed by default when =bb digest= runs
for the first time. To unsubscribe, send an email to the BARK inbox
with this body:

#+begin_example
Notify: off
#+end_example

To re-subscribe:

#+begin_example
Notify: on
#+end_example

** Setting preferences

Notification preferences are set via the same =Notify:= command.
Parameters can be combined on a single line:

| Parameter   | Description                        | Default |
|-------------+------------------------------------+---------|
| =d:N=         | Receive notifications every N days |      30 |
| =p:N=         | Minimum priority (0--3)            |       1 |
| =s:N=         | Minimum status (0--7)              |       1 |
| =m:<match>=   | Restrict to subject <match>        |         |
| =t:<topic>=   | Restrict to topic <topic>          |         |

Examples:

#+begin_example
Notify: d:7                 — every 7 days
Notify: d:1                 — daily
Notify: p:1                 — only important reports
Notify: d:3 s:4 p:2         — every 3 days, only open reports with priority >= 2
#+end_example

Like role commands, =Notify:= commands are only processed from direct
emails, not from the mailing list.

* Config
  :PROPERTIES:
  :CUSTOM_ID: config
  :END:

BARK is configured via a =config.edn= file.  Use =bb test-config= to
validate it.

** Minimal example

#+begin_src edn
{:admin "admin@example.com"

 :imap {:host     "imap.example.com"
        :port     993
        :ssl      true
        :user     "imap-login@example.com"
        :password "secret"
        :folder   "INBOX"}

 :db {:path "data/bark-db"}

 :sources [{:name       "my-list"
            :match      {:list-id "my-list.example.org"}
            :admin      "lead@example.org"
            :list-post  "my-list@example.org"}]}
#+end_src

** Source matching

Each source has a =:match= key that determines which emails belong to
it.  Two strategies are supported:

- =:list-id= --- matches the =List-Id= header (the identifier inside
  angle brackets, e.g. ="my-list.example.org"=).
- =:delivered-to= --- matches the =Delivered-To= header (useful for
  aliases or dedicated mailboxes).

As a fallback, a maintainer can add =[bark:<list-id>]= to the subject
of an email sent directly to the BARK inbox.  This is useful when the
email lacks the usual =List-Id= or =Delivered-To= headers.

** Source options

| Key                     | Description                                                      |
|-------------------------+------------------------------------------------------------------|
| =:name=                   | Source identifier (required)                                     |
| =:match=                  | ={:list-id "…"}= or ={:delivered-to "…"}= (required)               |
| =:admin=                  | Admin email for this source (required)                           |
| =:list-post=              | Mailing list posting address (for on-list/off-list distinction)  |
| =:list-archive=           | URL of the list archive (shown in HTML reports)                  |
| =:archive-format-string=  | URL template for message-ids (=%s= is replaced), used when the    |
|                         | =Archived-At= header is absent                                    |
| =:bark-path=              | Base URL where this source's public directory is served           |
| =:labels=                 | Per-source label overrides (see [[#customising-subject-labels]])      |
| =:triggers=               | Per-source trigger overrides (see [[#customising-trigger-keywords]])  |
| =:maintainers=            | Initial maintainers, e.g. =[{:email "dev@example.org" :since "2025-01-01"}]= |
| =:report-types=           | Restrict detected types, e.g. =#{:bug :patch}=                    |
| =:export-formats=         | Output formats, e.g. =["json" "rss"]=  (default: =["json" "org" "rss"]=) |
| =:export-reports=         | Restrict exported types, e.g. =#{:bug :patch :request}=           |
| =:expiry=                 | Auto-close delays in days (see below)                            |

The =:since= date on a maintainer entry restricts their privileges to
emails dated on or after that date.  Omit =:since= for immediate
effect on all emails.  Note: the admin is NOT automatically a
maintainer.

** Report expiry

Announcements, releases, and changes can be automatically closed
after a configurable number of days.  The close reason is set to
"expired".

#+begin_src edn
:expiry {:announcement 30
         :release      60
         :change       14}
#+end_src

This can be set globally or per source.

** Notifications (SMTP)

#+begin_src edn
:notifications {:enabled true
                :smtp {:host     "smtp.example.com"
                       :port     587
                       :tls      true
                       :user     "notify@example.com"
                       :password "secret"
                       :from     "bark@example.com"}}
#+end_src

** Logging

#+begin_src edn
:logging {:file     "logs/bark.log"
          :level    :warn
          :max-size "10MB"
          :backlog  5
          :email    {:to    "admin@example.com"
                     :level :error}}
#+end_src

Log file rotation is automatic.  Email alerts require SMTP to be
configured.

* CLI reference

All commands are run via [[https://babashka.org/][Babashka]]:

| Command              | Description                                              |
|----------------------+----------------------------------------------------------|
| =bb digest=            | Ingest new emails and create/update reports              |
| =bb digest --all=      | Re-process all emails from scratch                       |
| =bb export all=        | Export all formats for all sources                       |
| =bb export html=       | Export HTML pages only                                   |
| =bb export json=       | Export JSON feeds only                                   |
| =bb export rss=        | Export RSS feeds only                                    |
| =bb export org=        | Export Org feeds only                                    |
| =bb export stats=      | Export stats pages only                                  |
| =bb notify=            | Send notification emails                                 |
| =bb notify --dry-run=  | Preview notifications without sending                    |
| =bb clean=             | Remove all generated files (=public/=, =classes/=, =target/=) |
| =bb test-config=       | Validate =config.edn=                                     |
| =bb test-smtp=         | Test SMTP configuration (=--to addr=, =--dry-run=)          |

Export accepts flags: =-n <source>= (restrict to one source), =-p <N>=
(minimum priority), =-s <N>= (minimum status).

* Rationale
  :PROPERTIES:
  :CUSTOM_ID: rationale
  :END:

- *Email-native and immutable* :: BARK has no web form, no API endpoint,
  users don't have to create an account. Users report bugs and request
  features by sending an email to a list. Maintainers act by replying
  to that same thread: an =Acked:= line closes the report. Because every
  state change is encoded in an email, the entire tracker state can be
  reconstructed at any time by replaying the mailbox from scratch.

- *Statuses and priorities are derived, not asserted* :: BARK provides a
  short fixed vocabulary: =acked=, =owned=, =closed= for status; =urgency= and
  =importance= for priority. You cannot invent a custom =WONTFIX-MAYBE=
  status or manually set a report to P0.

- *No catch-all inbox* :: Most trackers (GitHub Issues being the
  canonical example) accept anything and leave triage as an exercise
  for the maintainer. BARK only ingests messages that match explicit
  subject- or body-trigger rules defined in =config.edn=. Most noise
  stays out of the tracker by design, not by discipline.

- *Local-first, workflow-agnostic* :: BARK exports to JSON, RSS, Org.
  Companion tools — =bone= (a TUI browser), =gnus-bark.el= (Emacs/Gnus
  integration) let each user consume the data in whatever environment
  they already live in, rather than forcing a new interface on them.
