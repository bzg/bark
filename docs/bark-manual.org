* EmBARK

_BARK_ is an email-driven report tracker.  A _report_ is an email
that BARK has classified from its subject label -- a bug, a patch,
a feature request, an announcement.  Subsequent emails in the same
thread can update the report's state through a small fixed
vocabulary of commands.

A maintainer can also write directly to the monitored inbox to
update reports, manage roles, and configure their digest emails.

BARK exposes its data as an HTML site and as JSON, Org and RSS
feeds.

* Example

Imagine Alice sends this email to a mailing list:

: From: alice@email.com
: Subject: [BUG] Wrong output
: To: project-mailing-list@lists.org
: Date: Fri, 6 Mar 2026 16:31:14 +0000
: 
: Hi all,
: 
: when doing X, I get the wrong output, probably a bug.

Then Bob replies:

: From: bob@email.com
: Subject: Re: [BUG] Wrong output
: To: alice@email.com
: Cc: project-mailing-list@lists.org
: Date: Fri, 6 Mar 2026 16:38:42 +0000
: 
: > when doing X, I get the wrong output, probably a bug.
: 
: Confirmed, I see this too, this should not happen.

And Eve, the maintainer, concludes:

: From: eve@email.com
: Subject: Re: [BUG] Wrong output
: To: project-mailing-list@lists.org
: Date: Fri, 6 Mar 2026 16:42:03 +0000
: 
: >> when doing X, I get the wrong output, probably a bug.
: 
: > Confirmed, I see this too, this should not happen.
: 
: Fixed in commit bc12c0c, thanks to both of you!

In this exchange:

1. Alice reported a bug.
2. Bob confirmed it.
3. Eve closed it.

All three saw the same emails -- the mailing list is the
conversation.  BARK indexes that conversation so the same
information becomes queryable as a database: a list of reports,
their states, their authors, their threads.

* Principles

BARK rests on four design choices.

- *Single source* :: Reports and discussions live in one place, the
  mailing list.  BARK indexes that archive; it does not host a
  parallel conversation.

- *Email-native* :: Every state change is encoded in an email.  A
  contributor who replies to a thread updates the tracker without
  leaving their mail client.

- *Reproducible state* :: The mailbox is the source of truth.  The
  tracker database can be rebuilt at any time from the archive.

- *Fixed vocabulary* :: The set of states is closed: =acked=,
  =owned= and =closed= for status; =urgent= and =important= for
  priority.  Companion tools (=bone= TUI, =gnus-bone.el=,
  =notmuch-bone.el=) read the same data without introducing a new
  interface.

* As a user
** Bug, Patch, Request

The subject label determines a report's type.  The three main
labels are =[BUG]=, =[PATCH]= and =[POLL]= or =[TODO]= for
requests; see [[#report-types][report types]] below for the full list.

A _patch report_ is created in two cases:

1. The subject starts with =[PATCH]=, either directly or as
   =Re: [PATCH] ...= when the reply carries a =.patch= or =.diff=
   attachment (the v2/v3 reply workflow).
2. The email attaches a =git format-patch= file whose inner
   =Subject:= header starts with =[PATCH]=.

A bare inline diff, a =git diff > x.patch= attached in a reply
without re-labelling, or a quoted diff in a discussion remain
regular replies.  To have BARK track such a fix as a patch, attach
a real =git format-patch= file or relabel the subject with
=[PATCH]=.

Attaching a patch to a =[BUG]= or =[FR]= email leaves the report's
type unchanged; the patch is stored as metadata on the parent.

** Setting a topic

A _topic_ is a short string attached to a report.  Set it from the
subject in one of two ways:

- Inside the label: =[BUG parser]= sets the topic to "parser".
- As a colon prefix after the label: =[BUG] parser: crash on empty
  input= also sets the topic to "parser" -- the segment before the
  first colon after the closing bracket.

To change the topic on an existing report, reply with:

: Topic: new-topic.

To remove it, reply with =No topic.=.

** Updating reports

A _command_ is a case-sensitive keyword recognised at the start of
a line in a thread reply.  BARK accepts a command when the keyword
is followed by punctuation (=.= =,= =;= =:= =?= =!=), by
whitespace, or by end of line.

For example, a reply to a bug starting with =Confirmed.= marks the
bug as _acked_; a reply to a patch starting with =Applied.= or
=Fixed.= marks the patch as _closed_.

The keywords =Urgent= and =Important= are stricter: they require
punctuation or end of line, because the same words appear too often
in ordinary prose ("Important note:", "Urgent matter").

BARK strips email signatures (delimited by =-- = per RFC 3676)
before scanning, so command-like words in signatures are ignored.

A reporter cannot ack their own report; =Acked= requires a second
party.  Ownership has no such restriction.

A command targets the thread, never the mail that carries it --
unless that mail opens its thread.  A root mail that introduces a
report (e.g. =[BUG] foo=) annotates that report; any reply hands
its commands to the nearest report in the thread, even when the
reply itself creates a new report (e.g. a =Re: [PATCH]= v2).

See the [[#all-commands][complete list of commands]] for the full registry.

** Retracting your own updates

To retract a state that you previously set with =Acked.=, =Owned.=,
=Closed.=, =Urgent.= or =Important.=, reply with the matching "Not"
command:

: Not acked.
: Not owned.
: Not closed.
: Not urgent.
: Not important.

Each retraction applies only to your own earlier action.
Maintainers have broader retraction rights, described in
[[#undoing-updates][Undoing updates]].

** Superseding a report

One report can replace another -- a newer patch version, or a
fresh bug report that captures the real issue.  Two equivalent
directives mark a supersession; which one you use depends on the
thread you write from.

From the old report's thread, write:

: Superseded-by: <new-message-id@example.com>

From the new report's thread, write (in a reply, or in the opening
mail of a new bug, patch or request):

: Supersedes: <old-message-id@example.com>

A _message-id_ takes one of three forms: =<id@host>=, the bare
=id@host=, or the last path segment of an archive URL such as
=https://list.orgmode.org/orgmode/id@host/=.  Both reports must be
of the same type: bug to bug, patch to patch, request to request.

To undo, reply with =Not superseded= from the closed report's
thread, or with =Not superseding= from the replacement's thread.

For the automatic actions BARK performs on supersession, see the
[[#superseding-a-report-1][maintainer section]].

** Marking a report as a duplicate

Use =Duplicate-of:= when two reports describe the same issue, and
=Superseded-by:= when a newer report replaces an older one.  The
typical case for a duplicate is two bug reports filed
independently; the typical case for a supersession is a patch v1
followed by a v2.

To mark a report as a duplicate of another, reply with:

: Duplicate-of: <target-message-id@example.com>

Message-id forms and type constraints match =Superseded-by:= (see
above).  The duplicate is closed with reason =:cancelled= and
linked to the target.  To undo, reply with =Not duplicate.=

** Cross-referencing reports

To cross-reference another report, reply with:

: Related-to: <other-message-id@example.com>

This directive accepts any pair of reports, including closed
ones, and uses the same message-id forms as =Superseded-by:=.
Several =Related-to:= lines in a single email post several links.
To undo a cross-reference, reply with =Not related-to:
<other-message-id@example.com>=.

** Resolving a bug or request with a patch

Replying to an open bug or request with a =.patch= or =.diff=
attachment credits you as =Acked= and =Owned= on that parent.
This credit only fires when the nearest parent is a bug or a
request.  When you are the parent's own reporter, only =Owned= is
credited.  An existing explicit setter is preserved; opt out with
=Not acked.= or =Not owned.=.

When the same reply also produces a separate patch report
(labelled =Re: [PATCH]=, or carrying a =git format-patch=
attachment), the patch is linked to the parent through a
=:resolves= relation.  Closing that patch with =Applied.= or
=Fixed.= then propagates the closure to the parent, with reason
=:resolved=.

Cancelling the patch retracts the implicit credit.  Superseding
it transfers =Owned= to the new author; =Acked= is historical and
stays with whoever first confirmed the parent.

The source-level =:patch-triggers? false= flag disables both the
implicit credit and the closure propagation.

** Voting on requests

Requests (=[POLL]=, =[TODO]= and their aliases) accept votes.
Reply to the thread with one of:

- =+1= or =1+= -- a positive vote.
- =-1= or =1-= -- a negative vote.
- =+0=, =0+=, =-0= or =0-= -- an abstention.

Each voter is counted once per report; the first vote wins.

* As a maintainer

A maintainer acts on a source through the same email channel as a
regular user, with broader permissions and a few additional report
types.  The sections below describe what is specific to that role.

** Announcements, releases, changes

In addition to bugs, patches and requests, a maintainer can post
general announcements (=[ANN]=), share a release (=[REL]=), or
announce an upcoming change (=[CHG]=) for a future release.

** Events (ICS calendar support)

An announcement can also carry a calendar event.  When an =[ANN]=
report contains an attached =.ics= file or inline =VCALENDAR=
content in the body, BARK stores the calendar data alongside the
report.  During export, such announcements are gathered into
dedicated event feeds:

- Individual =.ics= files are written to =events/<mid-hash>/=.
- Combined ICS calendar files:
  - =events/announcements.ics= --- all announcements with events.
  - =events/announcements-open.ics= --- open only.
  - =events/announcements-closed.ics= --- closed only.
- =events.json=, =events.org=, =events.xml= list open announcements
  with ICS content; =events-closed.*= list closed ones.

Use =[ANN event]= to set the topic to "event" for easier filtering,
but any announcement with ICS content is included regardless of topic.

** Undoing updates

A maintainer can undo any update on a report through the same
"Not" or "No" directives that a regular user has at their
disposal:

: Not acked.
: Not owned.
: Not closed.
: Not urgent.
: Not important.
: No deadline.
: No expiry.
: No topic.
: Not superseded.

A regular user can only retract their own actions (see
[[#retracting-your-own-updates][Retracting your own updates]]).  A maintainer applies the same
directives without that restriction.

** Setting a deadline

To set a _deadline_ on a report, reply with:

: Deadline: 2026-03-10.

The value is either an ISO date (=yyyy-MM-dd=) or a duration
(=2d=, =3w=, =1m=, =1y=) resolved relative to today.  A trailing
punctuation mark is optional.  Deadlines appear in JSON exports,
in Org output as a =DEADLINE:= line, and in notification emails.

To remove a deadline, reply with =No deadline.=.

** Setting an expiry date

A per-report _expiry date_ schedules the automatic closing of a
report.  When the date is reached, BARK closes the report with
reason "expired", overriding the source-level expiry rules.

To set an expiry, reply with one of:

: Expiry: 2026-06-15.
: Expiry: 30d.

Like =Deadline:=, the value is an ISO date or a duration.  The
expiry appears in JSON exports under =:expiry=, in Org output as
an =:EXPIRY:= property, and in the HTML index as a tooltip on the
date column.

To expire reports automatically at their deadline, use
=:inactive-after :deadline= in the source-level expiry rules (see
[[#report-expiry][report expiry]]).

To remove a per-report expiry, reply with =No expiry.=.

** Superseding a report

A =Supersedes:= or =Superseded-by:= directive (see [[#superseding-a-report][the user
section]] for syntax and message-id forms) triggers three automatic
actions:

1. BARK records a =:supersedes= qualified relation between the
   two reports, together with a symmetric =:related-to= audit
   link.
2. The old report is closed with close-reason =:superseded=.
3. The two reports are linked as related; the link survives an
   undo.

In the HTML index, a superseded report appears struck through,
with an "S" status flag.  Its subject tooltip shows the
replacement's title.

A later directive may flip the direction.  When =Supersedes: <X>=
is posed at time t1 and =Superseded-by: <X>= at time t2 on the
same report, the second pose retracts the first, reopens the
previously closed report, and applies the new direction.

To undo a supersession, the original setter or any maintainer can
reply with =Not superseded= or =Not superseding=.  Either form
retracts the relation, reopens the closed report, and clears the
close-reason; the =:related-to= link is kept.

*** Automatic supersession of patches

When a new patch report appears in a thread whose earlier open
patch report shares the same base subject (ignoring =Re:= or
=Fwd:= prefixes and =[TAG]= brackets), the new report
automatically supersedes the previous one.  This covers re-sent
patches without explicit version numbers.

For example:

#+begin_example
[PATCH] A new feature          : patch report (1)
  Re: [PATCH] A new feature    : patch report (2), supersedes (1)
    Re: [PATCH] A new feature  : patch report (3), supersedes (2)
#+end_example

Only the most recent patch (3) remains open.

The reply must itself qualify as a patch report -- either a
=Re: [PATCH]= subject with an attached patch, or a =git
format-patch= attachment.  A plain =Re:= without a patch carries
on as ordinary discussion.

Patches that carry an explicit version number (=[PATCH v2]=)
follow a separate mechanism, which matches on version and topic.

** Acting as an update proxy

A maintainer can update a report on behalf of another user by
writing directly to the BARK inbox with one of the following
directives:

: Acked-by: a-user@example.com
: Owned-by: a-user@example.com
: Closed-by: a-user@example.com
: Urgent-by: a-user@example.com
: Important-by: a-user@example.com

The RFC 5322 =Display Name <addr>= form is also accepted:

: Owned-by: A User <a-user@example.com>

** Managing roles and permissions

Permissions follow three rules:

- Each source has exactly one lead maintainer.
- Any maintainer can promote another user to maintainer.
- Only the lead maintainer can demote a maintainer back to user.

To change roles, write to the BARK inbox:

#+begin_example
Add maintainer: dev@example.com        (any maintainer)
Remove maintainer: dev@example.com     (lead maintainer only)
#+end_example

The RFC 5322 =Display Name <addr>= form is also accepted:

#+begin_example
Add maintainer: Dev User <dev@example.com>
#+end_example

State-changing actions (commands and role controls) must be sent
through the source's public channel -- the mailing list or alias.
That requirement ensures that every instance of BARK running on
the same source sees the same state.

Notification preferences, by contrast, are personal and may be
sent privately.

* Report types

BARK detects a report's type from its subject label:

| Tag                               | Type         |
|-----------------------------------+--------------|
| =[BUG <topic>]=                     | bug          |
| =[PATCH <topic> <version> <n/m>]=   | patch        |
| =[POLL <topic>]= or =[TODO <topic>]=  | request      |
| =[ANN <topic>]=                     | announcement |
| =[REL <topic> <version>]=           | release      |
| =[CHG <topic> <version>]=           | change       |

The long-form aliases =[ANNOUNCEMENT]=, =[RELEASE]= and =[CHANGE]=
are also accepted.  Labels are case-sensitive and require
whitespace (or end of subject) after the closing =]=.  Malformed
labels are ignored.  Posting an announcement, a release or a
change requires maintainer permission.

All =<…>= parts are optional and positional.  For =[REL]= and
=[CHG]=, a single value is interpreted as the =<version>=: =[REL
2.0]= sets the version to "2.0".  Pass both for topic and version,
as in =[REL parser 2.0]=.  For =[PATCH]=, =<version>= is a =v\d+=
token (e.g. =v2=), and =<n/m>= is a sequence marker (e.g. =3/5=).

When a =[REL <version>]= report is posted, any open =[CHG
<version>]= report with the same version is automatically closed,
and the two reports are linked as related.

** Patch series

A _patch series_ groups patches that share a sequence marker
(=<n/m>=).  A cover letter (=0/m=) or a fresh =1/m= patch from
the same sender and topic automatically closes the previous
series and starts a new one.  This is how a version bump
supersedes the previous run: sending =[PATCH parser v2 0/3]=
closes the earlier =v1= series for that topic.

** Customising subject labels

The labels in the table above are the built-in defaults.  Override
them globally or per source in =config.edn= through the =:labels=
key.  Only the types you list are affected; the others keep their
defaults.

#+begin_src edn
;; Global override (applies to all sources)
:labels {:bug     ["BUG" "DEFECT"]
         :request ["POLL" "FR" "TODO" "RFE"]}
#+end_src

#+begin_src edn
;; Per-source override (inside a source map)
{:name "my-list"
 :labels {:announcement ["ANN" "NEWS"]}}
#+end_src

A per-source setting takes precedence over the global =:labels=,
which in turn takes precedence over the built-in defaults.

* Commands

A _command_ is a keyword recognised at the start of a line in a
thread reply, followed by punctuation (=.= =,= =;= =:= =?= =!=),
whitespace, or end of line.  Two commands are stricter: =Urgent=
and =Important= require punctuation or end of line, never
whitespace (see [[#priority-commands][priority commands]]).

A _directive_ is a command that takes a parameter.  The directives
=Topic:=, =Deadline:=, =Expiry:=, =Acked-by:=, =Owned-by:=,
=Closed-by:=, =Urgent-by:=, =Important-by:= and =Superseded-by:=
require at least one whitespace character between the colon and
the value.  =Topic: parser= is recognised; =Topic:parser= is
silently ignored.

** Status commands

| Command keyword                         | Effect on report  |
|-----------------------------------------+-------------------|
| =Acked= =Confirmed= =Approved=                | acked             |
| =Owned=                                   | owned             |
| =Canceled= =Cancelled=                      | closed (canceled) |
| =Expired=                                 | closed (expired)  |
| =Resolved= =Applied= =Fixed= =Closed= =Completed= | closed (resolved) |

A report carries a combination of three states:

- =:acked= :: someone has taken the next sensible action --
  confirmed a bug, reviewed a patch, approved a request.
- =:owned= :: someone has claimed ownership of the report.
- =:closed= :: the report is resolved, canceled, or expired.

The numeric form of the status combines these three bits:

| (un)acked  | (0)1 |
| (un)owned  | (0)2 |
| (un)closed | (4)0 |

An acked, unowned and open report therefore has status =1+0+4 = 5=.

Only bugs, patches and requests carry an _acked_ or _owned_
state.  Announcements, releases and changes can still be marked
urgent or important, and can still be closed.

** Priority commands

| Command keyword | Effect on report  |
|-----------------+-------------------|
| =Urgent.=         | Mark as urgent    |
| =Important.=      | Mark as important |

=Urgent= and =Important= require punctuation (=.= =,= =;= =:= =?=
=!=) or end of line.  A bare space is rejected, since words like
"Important" appear too frequently in ordinary prose to be safe
triggers.

These two values combine into the numeric priority:

| (un)important | (0)1 |
| (un)urgent    | (0)2 |

A report flagged as both important and urgent therefore has
priority =1+2 = 3=.

** Multiple commands

You can use several keywords in the same email, one per line.

: From: x@y.z
: Date: Thu, 19 Mar 2026 16:45:00 +0100
: Subject: Re: [BUG] Crash on startup
:
: > Crash on startup with the new build.
:
: Confirmed.
: Urgent.
: Important.

** Customising commands

You can customize command keywords globally or per source.

*** Overriding words, permissions, and report types

Each entry is a map with any of =:words=, =:scope=, =:report-types=
(at least one must be present):

#+begin_src edn
:commands {:closed   {:words ["Canceled" "Fixed" "Wontfix"]}
           :acked    {:words ["Approved" "LGTM"]
                      :scope :maintainer}               ;; Restrict to maintainers
           :deadline {:report-types
                      #{:bug :patch :request :change}}  ;; Widen to changes
           :unclosed {:scope :setter-or-maintainer}}    ;; Override scope only
#+end_src

- =:scope= overrides the default permission for that command. Possible
  values:
  - =:user= -- anyone
  - =:maintainer= -- maintainer only
  - =:setter-or-maintainer= -- the address that previously set the
    attribute, or any maintainer (maintainers keep their administrative
    override)

  =:setter-or-maintainer= is only valid on unset directives whose
  target attribute is tracked by a ref to the pose-email: =:unacked=,
  =:unowned=, =:unclosed=, =:unurgent=, =:unimportant=, =:untopic=,
  =:undeadline=, =:unexpiry=, =:unsuperseded=, =:unsupersedes=,
  =:unduplicate=.  =bb test-config= rejects this scope on any other
  command.
- =:report-types= replaces the default set of report types the command
  applies to. When absent, the registry default is used.
- Any command ID from the table below can be overridden, both triggers
  and directives.
- Role controls cannot be overridden.

Per-source settings take precedence over the global =:commands=, which
in turn take precedence over the built-in defaults.

*** Syntax mode: =:loose= vs =:strict=

The =:command-syntax= key controls whether BARK instructions must
be prefixed with =!=.  The default is =:loose=; the opt-in
=:strict= mode requires the prefix on every command.  Strict mode
removes false positives on common English words such as "Done.",
"Closed." or "Applied." that appear naturally in conversation.

| Form             | Loose                  | Strict                 |
|------------------+------------------------+------------------------|
| Trigger          | =Closed.= / =!Closed.=     | =!Closed.=               |
| Negative trigger | =Not acked= / =!Not acked= | =!Not acked=             |
| =-by= directive    | =Acked-by: a@b.c=        | =!Acked-by: a@b.c=       |
| Date directive   | =Deadline: 2026-06-01=   | =!Deadline: 2026-06-01=  |
| Topic            | =Topic: event=           | =!Topic: event=          |
| Supersede        | =Superseded-by: <mid>=   | =!Superseded-by: <mid>=  |
| Supersede (sym.) | =Supersedes: <mid>=      | =!Supersedes: <mid>=     |
| Role control     | =Add maintainer: a@b.c=  | =!Add maintainer: a@b.c= |

Set globally or per source (per-source wins):

#+begin_src edn
:command-syntax :strict
#+end_src

**** Replaying archives under a different convention

When a source's vocabulary or syntax mode has changed over time (a
list that tightened from =:loose= to =:strict=, or accepted =Done.=
only during a specific era), declare the history inline with =:periods=
(see [[#source-periods][Source periods]]).  Each period carries its own overrides for
=:commands=, =:command-syntax= and =:maintainers=; the core resolves
the effective config at each email's date without any per-email
timeline logic.

** All commands

A _command_ is a keyword sent in a public reply, by a user or a
maintainer.  In the "Permission" column, "setter or maintainer"
denotes the user who previously set the attribute; a maintainer
retains a full override in every case.

| ID                 | Syntax / Words                              | Permission           | Report types        |
|--------------------+---------------------------------------------+----------------------+---------------------|
| =:closed= (resolved) | =Closed=, =Resolved=, =Applied=, =Fixed=, =Completed= | any user             | all                 |
| =:closed= (canceled) | =Canceled=, =Cancelled=                         | any user             | all                 |
| =:closed= (expired)  | =Expired=                                     | any user             | all                 |
| =:acked=             | =Acked=, =Confirmed=, =Approved=                  | any user             | bug, patch, request |
| =:owned=             | =Owned=                                       | any user             | bug, patch, request |
|--------------------+---------------------------------------------+----------------------+---------------------|
| =:urgent=            | =Urgent.=                                     | any user             | all                 |
| =:important=         | =Important.=                                  | any user             | all                 |
| =:topic=             | =Topic: word=                                 | any user             | all                 |
| =:superseded-by=     | =Superseded-by: <msg-id>=                     | any user             | all                 |
| =:supersedes=        | =Supersedes: <msg-id>=                        | any user             | all                 |
| =:deadline=          | =Deadline: 2025-03-19= or =Deadline: 30d=       | any user             | bug, patch, request |
| =:expiry=            | =Expiry: 2025-06-15= or =Expiry: 30d=           | any user             | bug, patch, request |
|--------------------+---------------------------------------------+----------------------+---------------------|

| =:closed-by=         | =Closed-by: addr@host=                        | maintainer           | all                 |
| =:urgent-by=         | =Urgent-by: addr@host=                        | maintainer           | all                 |
| =:important-by=      | =Important-by: addr@host=                     | maintainer           | all                 |
| =:acked-by=          | =Acked-by: addr@host=                         | maintainer           | bug, patch, request |
| =:owned-by=          | =Owned-by: addr@host=                         | maintainer           | bug, patch, request |
#+TBLFM: $1=:closed= (bug)

** All controls

A _control_ manages a role.  Role controls must be sent through
the source's public channel.

| ID   | Syntax / Words                 | Permission      | Channel |
|------+--------------------------------+-----------------+---------|
| role | =Add maintainer: addr@host=      | maintainer      | public  |
| role | =Remove maintainer: addr@host=   | lead maintainer | public  |

* Exploring reports

BARK exports its data as HTML pages and as JSON, Org and RSS
feeds.  This chapter describes the exported files and the
companion tools that consume them.

** Exported pages and feeds

Running =bb export all= generates, for each source:

- HTML pages: =index.html= (reports table), =stats.html= (charts),
  =docs.html= (user docs).
- Full exports: =all.json=, =all.org=, =all.xml=.
- Per-type feeds: =bugs.json=, =patches.xml=, =requests.org=, etc.
- =votes.json= --- per-report vote details (see below).
- =patches/= --- attached and inline patch files.
- =text/<mid-hash>/= --- =text/plain= and =text/x-log= attachments
  (backtraces, log files).
- =events/<mid-hash>/= --- =.ics= attachments from announcements;
  combined feeds at =events/announcements{,-open,-closed}.ics=
  aggregate VEVENT blocks for subscription.
- =events.{json,org,xml}= and =events-closed.{json,org,xml}= ---
  open/closed announcements carrying =.ics= or inline VCALENDAR content.

RSS feeds contain up to 50 items, most recent first.  Export is
incremental: only sources modified since the last export are
re-generated.  Use =--force= to rebuild everything, or =bb export
{json|rss|org|html|stats|text|events}= to rebuild a single format.

| Flag                  | Purpose                                                  | Configurable |
|-----------------------+----------------------------------------------------------+--------------|
| =-n <source>=           | restrict to one source                                   | --           |
| =-p <N>=                | filter by minimum priority                               | --           |
| =-s <N>=                | filter by minimum status                                 | --           |
| =--page-size <N>=       | paginate HTML report table (client-side rendering)       | CLI only     |
| =--closed-retention=    | exclude reports closed before given ISO date or duration | CLI only     |
| =--topics-filter=       | restrict to topics (comma-separated, case-insensitive)   | per source   |
| =--force=               | force a full re-export                                   | CLI only     |

Durations accept =Nd=, =Nw=, =Nm=, =Ny= (e.g. =--closed-retention 1y=
keeps reports closed within the last 12 months).

** Vote transparency

Each vote on a request is stored as a separate entity that records
its voter and its source email.  The export produces a
=votes.json= file for each source so anyone can audit the results:

#+begin_src json
{
  "<11@test.org>": {
    "+1": [{"voter": "alice@example.org", "message-id": "<12@test.org>"}],
    "-1": [{"voter": "bob@example.org",   "message-id": "<13@test.org>"}],
    "0":  []
  }
}
#+end_src

Each voter is counted once per report; the first vote wins.
Summary counts (=votes=, =votes-up=, =votes-down=, =votes-null=)
are still included in the per-report JSON for display, and are
derived from these entities at export time.

* Notifications

BARK can send email digests of open reports.  Subscribers and
their filters are declared by the operator in =config.edn=, under
=:notifications :subscribers= (see [[#notifications-smtp][Notifications (SMTP)]] under
Deploying BARK for the full configuration).

Each digest contains the failed commands relevant to the
recipient, the open bugs, patches and requests they own (with
upcoming deadlines first), and the open bugs, patches and
requests that nobody has acknowledged or owned yet.

** Subscribing or changing preferences

Subscriptions are not managed by email.  To subscribe,
unsubscribe, or adjust filters (minimum priority, subject match,
topic), ask the operator to edit =config.edn=.  This is a
deliberate trade-off: notifications are configured the same way
as SMTP and the maintainer list, so the operator owns the full
declaration of who receives what.

The =bb notify= task -- run by the operator from cron or a
systemd timer -- builds and sends the digests; =bb notify
--dry-run= prints them without sending.  Cadence is the
operator's choice; the task does not track per-recipient
intervals.

* Deploying BARK

This section addresses anyone running a BARK instance, whether for
an organisation, a project, or a personal mailbox on a single
machine.  BARK reads its configuration from a single =config.edn=
file; validate it after editing with =bb test-config=.

** Setting up an instance

The shortest valid configuration declares an IMAP mailbox and one
source:

#+begin_src edn
{:mailbox {:type     :imap
           :host     "imap.example.com"
           :port     993
           :ssl      true
           :user     "imap-login@example.com"
           :password "secret"
           :folder   "INBOX"}

 :sources [{:name        "my-list"
            :list        "my-list.example.org"
            :maintainers ["lead@example.org"]}]}
#+end_src

The =:db=, =:logging= and =:ingest= sections are optional.  Their
defaults are =:db {:path "data/bark-db"}=, stderr-only logging at
=:info= level, and =:ingest {:fetch {:limit 50}}=.  See
=config.edn.example= for the full annotated reference.

BARK also reads Maildir folders.  Point =:path= at the parent
directory that contains =cur/=, =new/= and =tmp/=, and use
=:folder= to select the subfolder.  Set =:folder ""= if the Maildir
at =:path= already holds =cur/=, =new/= and =tmp/= directly (no
subfolder).  A Maildir source in watch mode uses filesystem events
rather than polling.

#+begin_src edn
{:mailbox {:type   :maildir
           :path   "/home/me/Mail"
           :folder "INBOX"}
 :sources [{:name "my-list" :list "my-list.example.org"}]}
#+end_src

** Monitoring your local mail

BARK can run on a single machine to watch your own mail.  In that
mode:

- The mail source is a Maildir (see the example above).  Watch mode
  reacts to filesystem events -- no polling, no IMAP credentials.
- SMTP notifications are usually unnecessary: you're already reading
  the same mailbox BARK watches.  Either omit =:notifications= or
  set =:enabled false=.
- One source is enough.  Match on =:to= or =:list= depending on
  which header your local MDA stamps.

To keep BARK in the background, install the user-level systemd unit
from =docs/deploy/bark.service= (see [[#running-bark-in-production][Running BARK in production]]).

** Source types and matching

A source has exactly one type key, which determines how BARK
matches incoming emails:

- =:list= --- matches the =List-Id= header (bare identifier, e.g.
  ="my-list.example.org"=).  Emails are detected as list mail when
  =List-Id= or =X-BeenThere= is present.
- =:alias= --- matches =X-Original-To=, =Envelope-To=, =X-Envelope-To=, or
  =Delivered-To=.  Emails are detected as alias mail when the original
  recipient (from these headers) differs from =To=/=Cc=, or when multiple
  distinct =Delivered-To= values are present.
- =:to= --- matches =Delivered-To=.  This is for a dedicated mailbox
  where all emails are delivered directly.

Emails that match no source are discarded at ingestion.

** Source options

| Key                    | Description                                                                  |
|------------------------+------------------------------------------------------------------------------|
| =:name=                  | Source identifier (required)                                                 |
| =:list= / =:alias= / =:to=   | Exactly one (determines source type and header to match)                     |
| =:maintainers=           | Initial maintainers as a vector of email strings, e.g. =["dev@example.org"]=   |
|                        | The first entry is the lead maintainer (see [[#managing-roles-and-permissions][Managing roles and permissions]])  |
| =:list-archive=          | URL of the list archive (shown in HTML reports)                              |
| =:archive-format-string= | URL template for message-ids (=%s= is replaced), used when the                 |
|                        | =Archived-At= header is absent                                                 |
| =:base-url=              | Base URL where this source's public directory is served                      |
| =:labels=                | Per-source label overrides (see [[#customising-subject-labels][customising subject labels]])                  |
| =:commands=              | Per-source command overrides (see [[#customising-commands][customising commands]])                      |
| =:report-types=          | Restrict detected and exported types, e.g. =#{:bug :patch}=                    |
| =:export-formats=        | Output formats, e.g. =["json" "rss"]=  (default: =["json" "org" "rss"]=)         |
| =:expiry=                | Auto-close rules per report type (see below)                                 |
| =:notifications=         | ={:enabled false}= to silence notifications for this source (default: enabled) |
| =:awaiting-delay=        | Duration before flagging "awaiting reply", e.g. ="14d"= (default: 14 days)     |
| =:periods=               | Time-windowed overrides for maintainers/commands (see [[#source-periods][Source periods]])        |

** Source periods

When a source's vocabulary or maintainer list has evolved over time,
declare the history inline with =:periods= --- a vector of time-windowed
overrides.  Each entry may declare =:start= / =:end= (ISO =yyyy-MM-dd=)
plus any of =:maintainers=, =:commands=, =:command-syntax=, =:labels=.
Fields omitted in a period inherit from the source level, which
represents the current state.

#+begin_src edn
{:name "orgmode"
 :list "emacs-orgmode@gnu.org"
 :maintainers ["current-lead@example.org"]    ;; default + current era
 :periods
 [{:end "2020-01-01"
   :maintainers ["old-lead@example.org"]
   :commands    {:closed {:words ["Done" "Fixed"]}}}
  {:start "2020-01-01" :end "2024-01-01"
   :maintainers ["mid-lead@example.org" "co@example.org"]}
  {:start "2024-01-01"                         ;; last era, no :end
   :maintainers ["current-lead@example.org"]}]}
#+end_src

Rules:
- Periods must be /contiguous/: =:end= of era /N/ equals =:start= of era /N+1/.
- Only the /first/ period may omit =:start= (unbounded past).
- Only the /last/ period may omit =:end= (still active).
- =bb test-config= validates the periods and rejects gaps or overlaps.
- Maintainer tenure at each boundary is computed via /sync/:
  declared maintainers missing at the boundary are added,
  previously-active maintainers absent from the declared list are
  closed at the boundary's =:start=.
- =Add/Remove maintainer:= directives in emails continue to mutate
  tenures in real time /between/ boundaries.
- Sync is /idempotent/: re-running on an existing DB never duplicates
  tenures and does not reinstate maintainers closed by a past mail
  directive.  To replay from scratch (wiping mail-directive history
  along with everything else), run =clj -M:run -- --fresh=.

** Report expiry

Any report type can be automatically closed when its age and state
match configured rules.  The close reason is set to "expired".

Each entry under =:expiry= maps a report type keyword to a rule map:

| Rule key        | Type                      | Description                                             |
|-----------------+---------------------------+---------------------------------------------------------|
| =:inactive-after= | string / date / =:deadline= | Duration ("30d"), ISO date ("2026-06-01"), or =:deadline= |
| =:max-status=     | integer                   | Don't expire if activity score > this value (0--3)      |
| =:max-priority=   | integer                   | Don't expire if priority > this value (0--3)            |

All rules are conjunctive: a report is only expired when *all*
conditions are met.  Only =:inactive-after= is required; the others are
optional filters.

| =:inactive-after= value | Trigger                                                                |
|-----------------------+------------------------------------------------------------------------|
| Duration (e.g. =30d=)   | Last email in the thread is older than the duration (any reply resets) |
| ISO date              | The fixed date has passed, regardless of activity                      |
| =:deadline=             | The report's deadline is in the past (no deadline => never expires)    |

The =:max-status= value uses an activity score that only counts acked
and owned (since expiry candidates are always open reports):

| Score | Meaning          |
|-------+------------------|
|     0 | unacked, unowned |
|     1 | acked            |
|     2 | owned            |
|     3 | acked + owned    |

#+begin_src edn
:expiry {:announcement {:inactive-after "30d"}
         :release      {:inactive-after "6w"}
         :change       {:inactive-after "3m"}
         :bug          {:inactive-after "1000d"
                        :max-status 0      ;; only open, unacked, unowned
                        :max-priority 0}   ;; only non-urgent, non-important
         :request      {:inactive-after "1000d"
                        :max-status 0}}
#+end_src

This can be set globally or per source (per-source takes precedence).

In addition to these source-level rules, maintainers can set a
per-report expiry date using the =Expiry:= directive (see [[#report-expiry][report
expiry]]). A per-report expiry overrides the source-level rules: if a
report has an explicit expiry date, only that date is checked.

** Tuning ingestion

#+begin_src edn
:ingest {:fetch    {:limit 50}    ;; or {:since "30d"} or {:start "…" :end "…"}
         :max-size 1048576}       ;; skip emails > 1 MB (optional)
#+end_src

- =:fetch= -- first-run fetch window (no watermark yet).  Exactly one
  of three disjoint map shapes (no key mixing, empty map rejected);
  default is ={:limit 50}=:

  | Config form                      | CLI shortcut       | Meaning                                                                           |
  |----------------------------------+--------------------+-----------------------------------------------------------------------------------|
  | ={:limit N}=                       | =--fetch 50=         | Latest N messages (positive integer)                                              |
  | ={:since "Nd"}=                    | =--fetch 30d=        | Relative duration from now (=Nd=, =Nw=, =Nm=, =Ny=)                                       |
  | ={:start "yyyy-MM-dd" :end "..."}= | =--fetch 2020-01-01= | Absolute half-open window =[start, end)=; both keys optional, at least one required |

- =:max-size= -- skip emails larger than N bytes.  No limit by default.

Text content of =.patch=, =.diff=, =.ics=, =text/plain= and =text/x-log=
attachments is extracted and stored in the database. Attachments
larger than 1 MB (1,048,576 characters) are skipped with a warning --
only metadata (filename, size, content-type) is kept. Override the
limit with =:max-attachment-size= in the =:ingest= config section.

** Notifications (SMTP)

#+begin_src edn
:notifications
{:enabled true
 :smtp {:host     "smtp.example.com"
        :port     587
        :tls      true
        :user     "notify@example.com"
        :password "secret"
        :from     "bark@example.com"
        :reply-to "lead@example.com"}   ;; optional
 :subscribers
 {"a@example.org"
  [{:source "my-list"}]
  "b@example.org"
  [{:source "my-list" :min-priority 2}
   {:source "another-list" :topic "release"}]}}
#+end_src

Each key under =:subscribers= is a recipient's address.  The
associated vector lists their subscriptions, one per source --
a recipient on three sources receives three separate emails per
=bb notify= run.

Optional per-subscription filters:

| Key            | Description                                                  |
|----------------+--------------------------------------------------------------|
| =:min-priority=  | Min priority for the "unacked & unowned" section (default 1) |
| =:min-status=    | Min activity score for the "unacked & unowned" section       |
| =:subject-match= | Substring match on the report subject (all sections)         |
| =:topic=         | Substring match on the report topic (all sections)           |

=:min-priority= and =:min-status= only filter the "unacked &
unowned" section -- the section with the most volume.  Reports you
own (with or without deadline) are always listed regardless of
their priority or status.

=bb notify= does not track per-recipient cadence: it sends every
time it is invoked.  Schedule it from cron or a systemd timer.
=bb test-config= verifies that every =:source= named under
=:subscribers= matches an existing source =:name=.

A small operational state file, =public/.last-notify-failures.edn=,
records the last successful send per (subscriber, source) so the
same failed-command entries are not re-mailed at every run.  Delete
the file to replay all current failures on the next invocation.

** Logging

#+begin_src edn
:logging {:file     "logs/bark.log"
          :level    :warn
          :max-size "10MB"
          :backlog  5
          :email    {:to    "ops@example.com"
                     :level :error}}

** Running BARK in production

BARK can be deployed in two modes.

- *Watch mode under systemd* :: The daemon stays up, reacts to
  IMAP IDLE or Maildir filesystem events, and reconnects on
  failure.  A ready-to-edit unit file lives in
  =docs/deploy/bark.service=.  Install it to
  =/etc/systemd/system/bark.service= (root) or to
  =~/.config/systemd/user/= (user), then run =systemctl [--user]
  daemon-reload && systemctl [--user] enable --now bark=.

- *Batch mode under cron* :: The command =clj -M:run= is a
  one-shot: it connects, fetches new mail since the watermark,
  digests, expires, and exits.  Chain =bb export= and =bb notify=
  after it.  An example crontab lives in
  =docs/deploy/crontab.example=.

Either mode can be backed by an uberjar instead of =clj -M:run= to
avoid the Clojure startup cost on every invocation; see the Quick
start section of =README.org=.

** Maintenance

The =bb maintenance= task reports and prunes orphan emails.  Run
it while the daemon is stopped.

#+begin_src shell
bb maintenance                  # dry run, show orphan counts
bb maintenance --delete         # actually delete orphan emails
bb maintenance --verbose        # list individual orphan message-ids
bb maintenance --failures       # list recent command failures recorded
                                # for maintainers (denied actions, bad
                                # syntax, etc.)
bb maintenance --retention 6m   # override default orphan retention
                                # (90 days). Accepts "30d", "6m", "1y"
                                # or an ISO date.
bb maintenance -n my-source     # scope to a single source
#+end_src

An _orphan email_ is one that no report references and that no
maintainer has sent.

** Rebuilding history

A source's historical evolution -- vocabulary, syntax, maintainer
list -- is declared inline through =:periods= entries.  See
[[#source-periods][Source periods]] for the full format and rules.  At startup, BARK
materialises the tenure history by syncing at each period
boundary, and resolves the effective config for every email based
on its date.

To replay from scratch after editing periods (or after any config
change you want reflected retroactively), wipe the DB:

#+begin_src shell
clj -M:run -- --fresh   # interactive confirm, then full replay
#+end_src

=bb test-config= validates the =:periods= on each source: contiguity, ISO
date format, =:start= strictly before =:end=.

* Appendix 1: workflow examples

** Patch review cycle

A contributor submits a patch series:

: From: carol@dev.org
: Subject: [PATCH parser v1 0/2] Refactor tokenizer
: 
: Cover letter: this series splits the tokenizer into two passes.

: From: carol@dev.org
: Subject: [PATCH parser v1 1/2] Extract lexer phase
: 
: <inline patch>

: From: carol@dev.org
: Subject: [PATCH parser v1 2/2] Add second pass
: 
: <inline patch>

BARK creates a patch series (3 emails, cover + 2 patches).  The
maintainer reviews and asks for changes:

: From: eve@project.org
: Subject: Re: [PATCH parser v1 1/2] Extract lexer phase
: 
: > <inline patch>
: 
: The naming is confusing, can you rename foo to bar?

Carol resubmits as v2:

: From: carol@dev.org
: Subject: [PATCH parser v2 0/2] Refactor tokenizer
: 
: v2: renamed foo to bar as requested.

BARK automatically closes the v1 series and opens a new v2 series.
The maintainer applies:

: From: eve@project.org
: Subject: Re: [PATCH parser v2 0/2] Refactor tokenizer
: 
: Applied, thanks!

The v2 series is now closed (resolved).

** Maintainer triage

A bug comes in with no response for a while.  The maintainer triages
by replying to the list:

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Re: [BUG] Crash on startup
: 
: Confirmed.
: Owned.
: Urgent.

Later, the fix lands:

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Re: [BUG] Crash on startup
: 
: Fixed in commit abc123, thanks for reporting!

** Role management

Any maintainer adds a new maintainer (via the list):

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Role update
:
: Add maintainer: newdev@project.org

Only the lead maintainer can =Remove maintainer:=.

** Automatic expiry and override

With this config:

#+begin_src edn
:expiry {:bug {:inactive-after "90d" :max-status 0}}
#+end_src

A bug whose last email is 91 days old, still unacked and unowned,
is automatically closed with reason "expired" on the next expiry
run.

To keep a legitimately old bug open, a maintainer sets a
far-future expiry to protect it:

: From: eve@project.org
: To: bugs-list@project.org
: Subject: Re: [BUG] Legacy encoding issue
: 
: This is still relevant, keeping it open.
: No expiry.
: Owned.

Marking the bug as owned takes its status above =:max-status 0=,
so the expiry rule no longer applies.  =No expiry.= clears any
per-report expiry date previously set.
